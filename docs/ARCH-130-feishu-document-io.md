# ARCH-130 · 飞书文档 IO 的身份、工具分层与失败归类

## 0 · 一句话

飞书文档能力由五个部件叠成：**开放平台是地基，lark-cli 是引擎，vendor lark-\* skills 是引擎说明书，Link16 提供身份与凭据，repo-owned feishu skill 是唯一入口**；
`docio` 是这个入口里专管文档 IO 的那一格。

## 1 · 部件与调用方向

```text
人 / agent
    │  只认一个入口
    ▼
feishu skill（repo-owned·唯一入口）
    └── docio（文档 IO 能力域）
            │  ① 解析链接  ② 选身份  ③ 分派资源适配器  ④ 记账
            ▼
        lark-cli（vendor 引擎·命令面）
            │  逐进程凭据环境   决定用哪个应用（来自Link16名册）
            │  --as bot|user    决定用哪种身份
            ▼
        飞书开放平台（scope 校验 → 资源 ACL 校验 → 执行）
```

旁路部件：

| 部件 | 它是什么 | 它不是什么 |
|---|---|---|
| `lark-cli` | vendor 提供的命令行引擎，覆盖 docs / sheets / drive / base / whiteboard / im 等域 | 不是入口。agent 不直接调它，由 `docio` 调 |
| vendor `lark-*` skills | 每个域一份说明书，供 agent 查语义 | 不是入口，也不承载身份选择 |
| Link16 `feishu/` | 身份 registry、per-bot 应用凭据、桥、发送工具 | 不重新实现 lark-cli 已有的命令面 |
| `feishu` skill | 对人与 agent 的唯一入口 | 不把子命令细节复制成第二份文档 |

**为什么要收口**：vendor 侧现成能力散在数十个 skill 与数百条子命令上，入口一多就会出现
"同一件事三种做法、每种都缺一半权限"。`docio` 的价值不是重造命令，而是
**把身份、分派、覆盖率与失败归类这四件必须一致的事收进一个地方**。

## 2 · 身份模型：两种身份，永不混用

飞书有两种执行身份，它们的授权入口、有效期和署名都不同：

| | 应用身份（tenant） | 用户身份（user） |
|---|---|---|
| 代表谁 | 机器人自己 | 某个具体的人 |
| 授权入口 | 开发者后台应用权限页 | OAuth 设备码流程 |
| 有效期 | 应用凭据持续有效直至变更/撤销；访问令牌按接口到期时间自动获取 | 访问令牌与刷新凭据按实际到期时间处理，刷新失效时需重新授权 |
| 文档里的署名 | 显示该机器人 | 显示那个人 |
| 前置条件 | 需要资源被分享给该应用 | 需要那个人本身有权限 |

**默认规则（不可协商）**：

1. **谁在对话，就用谁的应用身份。** bot 身份来自桥在 spawn 会话时焊死的
   `FEISHU_BRIDGE_SESSION`，经名册解析到该 bot 自己的应用凭据，再以
   `LARKSUITE_CLI_APP_ID` / `LARKSUITE_CLI_APP_SECRET` 仅注入该次CLI子进程，
   显式 `--as bot` 执行。bot读写不依赖持久CLI profile，不再复制一份密钥配置。
   每次调用重新读取真源；继承来的其他应用/用户令牌不会进入该子进程。
   实际请求前复用Link16令牌换取函数，再通过该子进程的
   `LARKSUITE_CLI_TENANT_ACCESS_TOKEN`传递；vendor环境Provider本身不会替调用方换令牌。
   dry-run不换取令牌，也不发业务请求。
2. **解析不出身份就直接失败。** 不回退默认 profile、不借用别的 bot 的应用。
   共用一个应用外壳会让权限开在 A 身上、活由 B 干，并且文档里的编辑记录署名错人。
3. **用户身份只在"资源没分享给这只 bot"时作为显式兜底**，且必须播报剩余有效期。
   不自动发起OAuth，也不把应用权限与用户授权混成同一份凭据。

`.env`所指凭据是唯一维护入口，bot名是选择器，不是另一套App ID。
已有CLI profile仅保留给显式用户授权等兼容用途；使用前校验其App ID与名册一致。
同名但应用不同必须报告冲突，不能静默覆盖或借用。旧profile的存在不决定bot读写身份。
官方环境注入合同见[CLI嵌入说明](https://open.larksuite.com/document/mcp_open_tools/feishu-cli/embed-feishu-cli-in-agent.md)。

## 3 · 三类失败必须被区分

同一句"没权限"，在飞书那边其实是三件不同的事。混为一谈会导致"开了权限还是做不了"
或者"开了没用的权限"。

| 类别 | 机器信号 | 含义 | 正确动作 |
|---|---|---|---|
| **scope 层** | `missing required scope(s)` / `99991672` 并列出可替代 scope | 应用或用户的权限清单不够 | 按 SPEC-220 基线开通；若该 scope 需管理员审批则换免审批替代 |
| **资源层** | `40403` / `no permission … action: View, code: DENY` | 权限清单够了，但这份文档没分享给这个身份 | 把该 bot 加为文档协作者；**加再多 scope 都没用** |
| **能力层** | 接口本身不支持该资源类型 | 用错了 API（例如用文档接口读表格 token） | 走对应资源的适配器 |

`docio doctor` 的唯一职责就是把任何一次失败**准确地**落到这三格之一，并给出该格
对应的下一步。**禁止静默降级**：换身份重试而不告知，会让人以为权限已经配好。

## 4 · 四层内部结构

| 层 | 职责 | 不做 |
|---|---|---|
| **L1 Resolver** | URL/token → 资源类型、canonical token、wiki 解包、子资源清单 | 不发业务请求 |
| **L2 Identity** | 选身份与应用 profile；解析不出即失败；降级必须显式播报 | 不猜、不回退默认 |
| **L3 Adapter** | doc / sheet / bitable / whiteboard / media / comment 六个适配器，各自"取全 + 归一化" | 不各自定义身份或错误语义 |
| **L4 Ledger** | manifest：token、revision、抓取时间、覆盖率、未取到项及原因 | 不下结论说"读全了" |

**"是否读全"只认 L4 的 manifest。** 正文读取成功不等于嵌入表格、图片二进制、白板节点和
评论都取到了；覆盖率对不上就是没读全，由 `docio coverage` 机械判定，不接受自述。

## 5 · 与注册流程的关系

新智能体注册（SOP-120）产出的是**一个属于它自己的应用**。ARCH-130 要求：

- 注册完成时就按 SPEC-220 基线一次性开满免审批 scope，不留"用到才发现缺"的尾巴；
- bot文档操作直接消费已登记的应用凭据，不要求另注册CLI profile；
- 名册中的runtime `profile` 与CLI应用配置是不同概念；应用凭据只登记环境变量名，
  不记第二套身份，也不写死应用ID。需要显式用户授权时才保留经校验的CLI配置。
