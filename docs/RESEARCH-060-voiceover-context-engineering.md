# VoiceOver 上下文增长与视频制作

## 结论

本次最有证据的增长来源是：**任务恢复、规范和代码的大量读取，以及结果截断后的重新读取。**
视频图片也是输入的一部分，但不能把这次问题直接归为“成片太长、帧太多”。旧会话有一个零图片
输入阶段，单次输入仍增长至 233,408 token；新会话不到六分钟就达到 169,503 token。

改善方向是让 Agent 每一步取得足够且有效的信息，并让完整证据留在可查询文件里。规范完整性、
全片叙事与成片验收继续保留；重点减少重复输入、过时状态和无目标的资料展开。

上下文管理可以减少频繁压缩的压力，但不能据此承诺远程流不再超时。传输故障与看门狗恢复分别见
[RESEARCH-050](RESEARCH-050-voiceover-stream-timeouts.md) 和
[RESEARCH-040](RESEARCH-040-voiceover-watchdog-recovery.md)。

## 发现的具体问题

### 1. 全文读取反复发生，而且不全是 Agent 无故忘记

新会话第一次压缩前实际发出了 **51 次 Get-Content -Raw 命令，涉及 44 个不同路径**。
这是命令尝试数，不是 51 份全文都完整进入模型的证明。

| 重复读取对象 | 次数 | 工具结果批次 |
|---|---:|---|
| living-plan 上游 SKILL.md | 3 | 2、3、4 |
| 文档治理 SPEC-010-document-taxonomy.md | 3 | 2、3、4 |
| agent-profile-governance 上游 SKILL.md | 2 | 2、3 |
| build-episode-film.py | 2 | 11、13 |
| hyperframes-cli 的 preview-render.md | 2 | 13、14 |

第一次按要求读完整规范是必要工作。适配 skill 与上游 skill 的两次读取也不能简单算作同一文件重复。
可以改进的是：确认已经完整取得的内容是否真的需要再读，缺了哪一段，以及是否有文件更新。
“读过”必须能区分完整、部分、被截断；单独记一个文件名不够。

### 2. 并行读取的结果被外层截断，造成重新读取

28 批结果中，**13 批含 truncated output 提示，另有一批出现省略文本项**。
这里统计的是包含提示的批次，包含内层和外层截断，不是 13 个独立文件。

例如第 2 批同时读取多份完整规范，内层两条 shell 调用分别给 20,000 和 16,000 的输出预算，
外层没有提高默认 10,000 的总输出预算。合并结果显示原始 23,913 token，截去了 13,913。
随后第 3、4 批又读取其中的规范。这条时间线支持“截断后重读”的解释，不能据此推断 Agent 的内部动机。

结果是：正文进入一部分、缺失一部分、再补读一份；上下文增长与信息不完整可以同时发生。
把所有输出预算调大只能减少截断，不能减少输入量。应先按文件大小和读取目的安排批次，完整必读的
文档分批读完，普通代码与报告按章节、字段或定位结果读取。

第 12 批的 text(load("next2")) 等曾被怀疑为无意义重放。回查第 11 批有
[omitted 2 text items ...]，所以不能把这次补取直接列为已证实浪费。

### 3. “只读第一项”的 PowerShell 写法实际读了全文

现场出现两次：

~~~powershell
Get-Content -Raw <文件> | Select-Object -First 1
~~~

-Raw 先把整份文件变成一个字符串，-First 1 选中的就是这个完整字符串。
对现场的 find_session.py 做只读复现：前者返回 **4,421 字符**，而真正读取首行只返回 **22 字符**。
另一处对象是 build-episode-film.py。这个错误确实存在，但不是 20 多万 token 增长的全部原因。

若目的确实是前 N 行，使用 Get-Content -LiteralPath <文件> -TotalCount N；若要找某个行为，先用
rg -n 定位，再读相关代码块。必读完整文件仍要完整阅读，不能用首行取代要求。

### 4. 恢复成本里混入了大量历史，而当前状态又没有及时记录

第 8、9 批通过脚本分别展开旧会话用户消息和尾部工具记录，两批合计返回 **58,015 字符**；
不是把 119 MB 的原始会话一次全部塞入模型。用户截图、源代码、技能说明也在这个阶段陆续进入。

更关键的是状态有效性：PLAN-301 的 22:20 恢复记录明确写出，旧计划漏记了 21:14 的视觉否决。
因此接手者必须从聊天补回“技术检查通过，但这一版视觉已被用户否决”的事实。
这属于可见的状态记录滞后；没有证据证明一定是压缩删除了这条信息。

当前计划全文约 8,998 字符，其中现状段约 1,617 字符，历史回执约 2,615 字符（调查时快照）。
已有分区可供定向读取，不必另建一套互相竞争的项目真源。关键决策应及时进入现状；历史负责溯源。

### 5. 画面检查工具本身已经做对了一部分

capture-episode-runtime.mjs 将详细观察写入 observations.json，标准输出只给进度和汇总。
本次 240 个采样的文件为 **974,293 字节**，不是这 240 个完整对象直接进入了模型。

本轮离线实验从该文件生成包含方法、输入哈希、通过/失败计数、全部失败样本及证据路径的投影，
体积为 **3,331 字节**。逐条复核 240 个样本的三类检查结果与汇总完全一致，原文件保持不变。
文件体积减少 99.66%，说明可查询证据与工作摘要能够分开。

**这不是本次生产上下文节省了 99.66%，也不是新优化了该 runner。** runner 原本就输出简短统计。
真正需要避免的是后续又把完整观察文件读进主会话。摘要通过也不代表已经完成像素、审美、音轨或
运动语义验收；各类原始证据和相应检查仍需保留。

## 需要更新的 context engineering 认识

| 容易混淆的对象 | 在本项目中应怎样理解 |
|---|---|
| 聊天窗口里看见的字数 | 只是部分输入。运行规则、技能正文、工具参数、返回结果、代码补丁和图片也参与上下文 |
| 当前窗口与累计 token | 第一阶段累计输入约 449.7 万，是多次请求反复计入历史；峰值单次输入是 24.52 万 |
| 缓存与容量 | 最后一次输入 245,206，其中缓存 240,768，命中约 98.2%；仍接近窗口上限 |
| 图片文件大小与 token | 图片按模型的视觉处理规则计入；不能把 JSONL 里的 Base64 字符直接当成文字 token |
| 存到磁盘与释放上下文 | 文件落盘便于以后查询；已经输出进本会话的正文不会因“另存一份”自动消失 |
| 写摘要与压缩 | 在旧历史后追加摘要，不等于旧历史已被移出；真正的窗口重组要由运行时压缩或新阶段会话实现 |
| 自动压缩与项目记忆 | 压缩帮助接续，完整事实、用户否决、版本绑定与验收记录还应有可复核的持久来源 |

OpenAI 将窗口定义为单次请求能够容纳的 token 范围；输入、输出和适用模型的推理也受其约束。
现场第一阶段累计生成的推理 token 为 4,520，没有依据把 xhigh 认定为这次增长的主因。
[OpenAI Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)

缓存复用已有前缀的计算，主要改善输入处理成本和延迟；缓存 token 仍属于输入。
因此“缓存很好但窗口快满”完全可以同时成立。
[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

图片输入的处理与尺寸、模型及 detail 有关；降低 JPEG 字节数不等于同比减少视觉 token。
字体和遮挡验收需要足够清晰的画面，不能为了缩小上下文把关键细节降没。
[OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision)

压缩用于减少上下文并保留后续状态；具体保留策略由所用运行时决定。不能把另一产品的“保留最近几份文件”
直接当作现场 Codex 的合同，也不要手工改运行中的 rollout 来删除历史。
[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)

在更一般的 Agent 设计里，可使用文件标识按需取资料，并把阶段状态持久化；选择进入下一步的信息
应当是持续工作。它与一次性写好开场提示词是不同的工程职责。
[Anthropic 的 context engineering 实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 视频项目应如何组织信息

建议沿用现有 PLAN、节目时间轴和验收文件，增加清晰的读取与接续边界。无需先建设向量数据库或重写整套制作系统。

~~~mermaid
flowchart TD
    A[原始素材、逐字稿、逐帧观察及验收证据] --> B[按章节、时间段、来源 ID 查询]
    B --> C[当前片段的修改任务与必要证据]
    D[全片目标、叙事顺序、事实约束、最新用户决策] --> C
    C --> E[制作与检查]
    E --> F[有效版本、未通过项、证据路径、下一动作]
    F --> D
    E --> A
~~~

| 信息 | 保留位置和进入会话的方式 |
|---|---|
| 全片叙事与共用约束 | 当前计划/相关规范保留章节目的、事实、统一术语、声音交接、全局进度计算；按适用规则完整取得必要规范 |
| 当前片段 | 给出章节/事件 ID、全局帧段、相邻片段、当前输入版本、最新修改目标和必过检查 |
| 原始证据 | 时间轴、312 条字幕、素材溯源、完整采样结果留在文件；按 ID、时间范围、失败类型查询 |
| 视觉检查 | 按具体语义问题组织原帧和运动证据；结果写明时间点、通过/未通过及对应版本，继续保留必要审片覆盖 |
| 接续状态 | 用户否决、已验收输入、未解决问题、运行中任务、下一命令和证据索引及时更新，旧回执作为历史 |

一个真实的接续信息应明确表达：

> PLAN-301 当前共用铭牌/片尾修订接续；21:14 用户已否决旧视觉，旧技术通过不能继承为视觉通过。
> 字体精确匹配仍待确认。节目时间轴曾处于已编译但未接入成片状态，继续前要查当前消费者及对应验收，
> 不凭旧混音文件存在就宣称原声已经进入成片。

这段仅展示应保留的状态类型，不替代会变化的 PLAN 或完整制作规范。
当前任务包也必须携带全片约束；否则按章处理可能导致单位、来源结论、人物称谓、转场和全局时间相互冲突。

以后若采用专门审片 worker，收益取决于是否把细节留在该 worker、仅回传可追溯结论。
把整份历史复制给所有 worker、再收回全部原始日志，会扩大总负载。多 Agent 是可选组织方式，
本轮没有启动新 worker，也不把它列为最小修复的前置条件。

## 最小改动与验收顺序

1. **先修读取方式。** 消除 -Raw | Select-Object -First；代码按目标读取；完整必读文档按大小分批，
   明确检查结果是否截断。并行调用继续使用，但合并后的总输出也必须可控。必要全文只要已经完整读到且未改变，
   不重复加载；被截断时补缺失部分，不能假称读完。
2. **收紧工具回传。** 沿用现有检查器的摘要输出，保留证据路径、方法、输入绑定和全部问题索引。
   大量失败时分页读取完整问题清单，不能只截取前十项后声称其余通过。查询结果要能回到原始帧和音轨。
3. **让现有 PLAN 能直接接续。** 用户每次否决或改变范围时更新当前状态；记录替代关系，区分技术通过与视觉通过。
   恢复先读当前状态、最近用户决策和对应产物，再按缺口查旧聊天；避免每次恢复都重新展开全部用户历史。
4. **再试阶段边界与窗口预算。** 按“恢复结束、样片定稿、整片装配”等可验证边界接续。
   先测单次输入、每完成一个有效步骤新增的输入、截断次数和恢复读取量，再决定软预算或提前压缩点。
   不把未知阈值写成官方最佳值，也不靠频繁重开会话掩盖高昂的重新加载成本。

验收用同一项 21:14 视觉反馈和同一组只读素材做恢复对照：

- 必须找回视觉否决、最新署名要求、未确认字体、当前有效输入、全部未完成阶段和下一验证动作。
- 必须能把每个“已通过”指向当前输入版本及实际证据；故意换成旧版或删除关键输入时，不得沿用通过状态。
- 记录首个正确制作动作前的单次输入量、全文重读数、截断提示数及恢复耗时，与本次 169,503 token 的
  恢复阶段记录对比。减少量由实测报告，不预先承诺百分比。
- 重复读取预算下降之后，仍用完整语义、声音、字幕和画面验收验证结果。只看 token 下降不算通过。

本轮完成的是调查、读取错误复现和证据摘要实验；尚未部署上述读取/接续策略到正在工作的 VoiceOver。
不会把离线摘要体积变化说成生产效果，也不保证它能修复网络或服务端压缩失败。

## 复核入口与统计限制

- 本机聚合证据：[voiceover-context-engineering-evidence-20260912.json](../feishu/_state/voiceover-context-engineering-evidence-20260912.json)。
- 本机重跑脚本：[context-engineering-audit-20260912.py](../feishu/_state/context-engineering-audit-20260912.py)，运行
  python feishu/_state/context-engineering-audit-20260912.py。两者位于 gitignored 状态目录；报告随仓库可保留，
  本机证据文件不会自动随 Git 发布。脚本从 registry 解析 cxp home，固定统计截止到 23:51:34，输出审计前缀摘要哈希。
- 原始 token 用量事件常在工具返回后才落盘。紧跟第 N 个结果的用量属于生成第 N 个调用的请求，
  不能把这个数与前一个数相减后直接标成“第 N 个工具的精确成本”。本报告使用阶段用量与独立工具体积。
- 51/44 只统计新会话第一次压缩前的 Get-Content -Raw，不包含其他全文读取方式。
- 528,722 字符包括可见包装和截断提示；7 张是新加入的图片项，不把压缩替换历史中的旧图片重复计数。
- 本次没有精确到每份文件的模型 tokenizer 账单，也没有逐图 usage 明细。未把字符、字节、图片编码与 token 混算。
- 部分读取是规范明确要求；本报告不把读完整规范等同浪费。规范精简若以后进入实施，应走原有语义治理，
  保留原约束并按任务路由，不能未经验证删去验收规则。
