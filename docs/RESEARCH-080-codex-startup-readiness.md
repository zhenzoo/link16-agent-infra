# Codex 在 wmux 中为何空白等待，以及怎样恢复快速启动

本次查实并修复的是桥接启动设计中的额外依赖：旧流程要求模型先回答一次 READY，才打开官方终端；模型请求一旦慢或失败，本机界面就被一起挡住。普通 Windows Terminal 中的 `cxp` 没有这个前置任务，所以能先显示界面。修改后，真实 wmux 新建 workspace 到桥确认可用为 **4.1 秒**，到输入回显为 **4.5 秒**；故意给模型后端设置不可用的代理，也能取得本地会话就绪回执。

代码、隔离真机验收和完整回归已经完成。指定的 voiceover 生产桥已在 9 月 13 日加载更新，原 Codex 会话保持运行；新的启动流程在下次新建或恢复 worker 时使用，不代表全机旧进程已经热加载。生效范围见文末。

## 空白等待是怎样发生的

原来的顺序是：wmux 创建 workspace，依次输入 `bash`、`cd` 和带环境变量的 worker 命令，每行都发送 Enter。命令中的 outbox 目录告诉回传程序把结果写在哪里，CODEX_HOME 指定这个 profile 的配置和会话位置；这些赋值本身不需要网络响应。最后的 Python 命令已经执行，空白并不是漏了最后一次回车。

Python worker 随后启动本机 app-server、初始化连接、创建线程，**在打开终端之前**发送 `Reply exactly LINK16_APP_SERVER_READY.`，等待模型回合完成。这个预热最多等 120 秒，桥给整个启动 150 秒；如果最终回到裸 shell，旧桥还可能重发一次。120/150 秒是超时上限，不是每次必睡满的计时器，但它们把一次不必要的模型依赖放大成了分钟级空白。

预热原本补的是一个真实约束：安装的 Codex 0.154.0 不允许用 `thread/resume` 恢复尚未落盘的空线程。直接删掉预热、继续恢复这个新建空线程，实测会报 `no rollout found`。因此根治不能只是把超时调小；应该让官方终端自己走原生的新建流程，已有历史才走恢复流程。

另有两个独立问题让体验更差：

1. Python 观察连接早已明确直连本机，但原生 remote TUI 仍继承 HTTP/HTTPS/ALL_PROXY。不可用代理的对照实验中，本机终端接入也失败了。现在仅为 remote TUI 去掉代理变量，本机连接直连，真正负责模型请求的 app-server 保留原代理。
2. 旧启动提示协程调用了它作用域之外的 `reply`，到该发进度时会抛错。因此原本的“每 30 秒提示还在启动”也不能可靠显示。现在通过参数传入当前消息处理器的回传函数，测试实际执行协程并验证收到阶段与耗时。

## 修改后每一步凭什么继续

| 步骤 | 动作与继续条件 | 用户可见的信息 |
|---|---|---|
| 1. 提交启动 | 新 workspace 收到一条短脚本命令与 Enter；脚本顺序确认 cwd，再执行 registry 生成的 worker 命令 | 不再逐行粘贴长串环境变量并读屏猜 shell 状态 |
| 2. 连接本机服务 | worker 写入本次启动标识并启动 app-server；JSON-RPC 初始化成功才继续 | 启动命令已执行，正在启动本地 Codex 服务 |
| 3. 打开官方终端 | 独立回传进程先连到本地事件入口；官方 TUI 自己发送新建或恢复请求 | 正在打开 Codex 终端；首次任务前不调用模型 |
| 4. 确认同一会话 | 本地网关对应请求 ID 核对成功响应中的线程 ID 和 cwd；回传进程确认绑定该线程后，将成功响应交给 TUI | 正在创建／恢复会话，或确认同一会话的回传连接 |
| 5. 放行任务 | 桥核对本次启动标识、会话响应来源、线程 ID 以及活的 worker/TUI/observer，立即结束等待 | 会话与飞书回传均已就绪 |

终端接管屏幕之前，worker 直接输出短提示。终端接管后，桥每 5 秒检查真实阶段，阶段有变化就回传，停在同一步较久则每 15 秒补充耗时。错误和阶段同时写入本地状态；连接关闭或进程明确退出会直接失败，不再等满超时，也不把启动命令重新塞进终端。默认 60 秒是桥的故障等待上限，正常路径没有“先等 60 秒”的步骤。

## 为什么这次的结构化信号更有价值

端口能连上，只能证明服务在监听；创建了 TUI 子进程，只能证明操作系统接受了启动请求；看到输入框，也不能证明终端已经接上会话。这些都不能单独作为就绪证据。

本次还否决了一个看似更简单的方案：先给独立观察进程订阅，再等 `thread/started`。实测第二条原生连接能够收到“线程已创建”，却收不到随后正式回答。若仅凭该通知宣布完成，就会从“启动慢”变成“界面能用但飞书没回复”。

现在网关检查的是**官方终端自己发出的会话请求及其成功响应**，回传进程消费的是**这个终端实际收到的同一条事件流**。事件沿用既有 milestone 白名单；子线程、推理和原始工具输入输出不进入回传队列。独立观察进程仍可单独重启；尚未确认的允许事件留在有界内存队列中，重连后重放。这是确认消费的传输机制，不承诺整个 worker 崩溃后内存事件仍能恢复，也不把它宣称为端到端恰好一次投递。

这些都是官方终端完成会话接入所必需的交互，独立于 banner、建议文案和语言设置。依据包括 [官方 app-server 文档](https://developers.openai.com/codex/app-server/) 与本机安装的 0.154.0 所生成的 schema、[对应版本官方源码](https://github.com/openai/codex/tree/rust-v0.154.0/codex-rs)。它不等于协议永远不会变：如果将来成功响应缺少必需字段，代码会明确报协议不兼容并拒绝注入任务，升级验收应运行下列契约与真机用例，不能悄悄换成读屏或延长等待。

## 已经验证到什么程度

以下为本机 cxp、voiceover cwd、Codex 0.154.0 的独立测量，不是所有机器的速度承诺。每个用例使用独立状态目录和诊断 bot，不向飞书联系人发送测试消息；正式答案验至本地 outbox，原共享 drainer 的飞书网络投递没有在本次真发重测。

| 用例 | 观察结果 | 本地证据 |
|---|---|---|
| 真实 wmux `ensure_session` | 4.094 秒确认就绪，4.547 秒回显草稿；实际只提交一条启动脚本命令 | `feishu/_state/startup-1110/wmux-direct/result.json` |
| 独立终端新会话 | 5.406 秒确认就绪；提交正式提示后收到 typed final | `feishu/_state/startup-1110/mirror-online/worker-result.json` |
| 已有会话恢复 | 5.047 秒确认就绪；仍是原线程，正式回答进入 outbox | `feishu/_state/startup-1110/mirror-resume/worker-result.json` |
| 后端代理不可用 | 4.546 秒确认就绪，4.859 秒回显本地草稿；未发模型任务 | `feishu/_state/startup-1110/mirror-offline-direct/worker-result.json` |
| 只终止独立观察进程 | 约 4.5 秒重新绑定原线程，原 TUI 持续运行，下一条正式回答进入 outbox | `feishu/_state/startup-1110/mirror-observer-restart/worker-result.json` |
| 协议和故障回归 | 旧／错启动标识、死进程、缺字段不放行；真实连接断开立即唤醒请求；大帧原样通过；未确认事件重放；回传提示调用可达 | `tests/test_codex_startup.py` |
| 仓库完整回归 | 共运行 634 项，结果 OK、其中 1 项跳过；已有未关闭 asyncio loop 的 ResourceWarning 仍在 | `feishu/_state/startup-1110/full-tests-final.txt` |

调查中“失效代理下看到输入框”只是初步视觉结果，后来完整协议探针证明仍可能接入失败。上表采用修复后成功取得真实会话回执的结果，不将这个早期视觉判断当作断网启动验收。

## 当前生效范围与生产应用步骤

磁盘上的 worker、桥、wmux 启动原语、契约测试和 ARCH-110 已更新，保留本轮之前已有的 provider、quota 和 watchdog 改动。下一次新建 worker 会读取新代码；已经运行的 worker 和桥不会自动热加载。

只对这次故障对象 `tb24-voiceover` 应用桥侧更新，具体操作是 `python feishu/feishu_bridge.py start --bot tb24-voiceover`：由现有服务锁机制替换其桥进程，然后核对旧 PID 退出、新 PID 持锁、连接日志恢复。它不执行 `/close`，也不替换正在运行的 Codex 会话；新启动命令、严格就绪检查和进度提示将在之后创建会话时使用。其它 bot 的桥侧代码在各自后续正常重启时加载。

初次调查时桥 PID 为 39856，尚未更新。之后 owner 批准指定 bot 的维护窗口，PLAN-1120 完成入站持久交接与生产加载；23:29 又载入同回合交互后继续发进度的修正，桥 PID 为 50136。飞书真实回执确认进度恢复，原 worker、观察者与终端保持运行。具体经过、验证和剩余边界见 [RESEARCH-090](RESEARCH-090-bridge-restart-continuity.md)，不能把指定桥已更新扩大为所有 bot 均已更新。
