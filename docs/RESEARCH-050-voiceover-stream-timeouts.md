# tb24 VoiceOver 重连与远程压缩超时

## 当前判断

已证实的直接故障是：Codex 向 OpenAI 请求后，等待远程响应流超时；普通生成和上下文压缩两条路径
都出现过。用户贴出的本地画面检查已经完成，不能把后面的重连时间算作仍在运行本地检查。

最明显、可直接改进的放大因素是上下文增长过快：新会话约 24 分钟从 3.6 万增长到 24.5 万输入 token，
逼近本次实际有效窗口 25.84 万；接着约 26 分钟反复重试压缩。这个因素解释频繁触发压缩和重试的
暴露机会，尚不能单独证明每次断流的网络或服务端根因。

现有证据不足以判定“tb24 硬件差导致”；也不足以排除代理节点、远端服务或客户端流处理问题。
tb26 尚未取得同条件日志，不能用新旧电脑的印象代替对照。

## 本次现场时间线

以下均为 2026-09-12 北京时间。新 thread 为 `01a095f6-04d8-7e11-bea9-580c3285adc5`，
旧 thread 为 `01a09148-6a99-7b51-84e8-fda27d3d1e3d`；profile 为 `cxp`。

| 时间 | 记录 | 判断 |
|---|---|---|
| 22:12:03 | 新 VoiceOver thread 建立 | 后面的失败也发生在新会话，单纯换 thread 未消除问题 |
| 22:12:40 | 输入 36,136 token | 新会话起始负载 |
| 22:26:44 | 普通生成 WebSocket idle timeout，开始重试 | 故障不限于压缩 |
| 22:36:09 | 含 `opening-runtime-v4` 的工具调用回传，执行退出码 0 | 本地检查已经返回 |
| 22:36:40 | 输入 245,206 token | 24 分钟接近有效上下文窗口 |
| 22:41:43 | remote compaction v2，WebSocket 重试 1/2 | 压缩响应流超时 |
| 22:47:11 | WebSocket 压缩重试 2/2 | 继续消耗等待时间 |

| 22:52:51 | HTTPS 响应状态 200 | 请求已获响应；不等于完整流已结束 |

因此，屏幕上的二十多分钟主要是多次请求、等待、重试与协议切换累计，不能解释成某条本地 Node
检查一直没有结束。WebSocket 和 SSE 是两种接收增量响应的方式；两种都超时，不能认定只关掉
WebSocket 就能根治。

旧会话记录有 8 次 `compacted` 成功，以及 04:20、04:42、16:44、22:09 四次以远程压缩错误结束的
回合。成功事件数与失败回合数口径不同，不能直接据此计算压缩失败率。

## 为什么 VoiceOver 特别容易遇到

本机实际版本为 Codex 0.154.0，模型 `gpt-6-astra`，推理强度 `xhigh`。模型缓存给出的窗口为
272,000 token、有效比例 95%；rollout 实际报告 258,400。未发现用户配置主动覆盖自动压缩阈值。

新会话第一次压缩前，28 次工具结果合计包含约 528,722 字符文本和 7 张输入图片。其中，调用中含
`Get-Content -Raw` 的结果贡献 423,068 字符，约占文本的 80%。单个全文读取调用多次返回约
3.3–4 万字符。该统计是工具返回文本字符量，不是有效输入 token 的直接换算；实际 token 以
rollout 的 `last_token_usage.input_tokens` 为准。

旧会话文件约 119.6 MB；最大工具结果约 6.6 MB，几乎全部为四张图片的编码数据。这不表示每次
都上传 119.6 MB，也不能把图片编码字符直接当作文字 token。

同一 tb24 上的 Link16 会话也出现普通生成断流、TLS 异常关闭和远程压缩超时，18:42 也切换过 HTTP。
所以问题不只存在于 VoiceOver 工程。VoiceOver 的大量全文读取、验图和长时间任务让它更频繁
进入大上下文与压缩阶段，是当前最有证据的工作负载差异。

## 网络与电脑检查

实际链路经进程环境和 TCP 连接同时核对：VoiceOver Codex PID 43896 使用
`HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:7897`，连接确实进入该端口；监听者是
`AtlasCore_amd64.exe`，PID 24200。当前进程自 9 月 10 日启动，本次没有替换其节点或配置。

对实际 OpenAI 源站 `https://chatgpt.com/backend-api/codex/models` 做无凭据短探针：

| 路径 | 三次结果 | 能证明什么 |
|---|---|---|
| 现有代理 | 401，耗时 0.58 / 0.58 / 0.72 秒 | 源站当前可达；401 是探针未携带登录凭据的预期结果 |
| 绕过代理 | 三次连接超时 | 本次测试下直连不能替代现有代理 |

短探针不是生成请求，不能证明数分钟的 WebSocket/SSE 稳定性，也不能证明代理清白或有罪。
代理应用当天日志只有 8 字节，无法提供与失败时刻对应的传输诊断。未读取其安全存储文件。

本机资源采样：Ryzen 7 7735H；CPU 约 23–34%，可用物理内存约 8–11 GB，Windows 提交内存
占上限约 71–83%，数据盘可用约 248 GB，采样时磁盘队列为 0。24 小时 System 错误查询只返回
一条 Windows Update 失败，没有对应硬件、磁盘或资源耗尽错误。页面读取指标偏高，但这是瞬时
采样，调查中的数据库读取也会影响该指标，不能直接解释为内存不足。

这些结果不支持当前存在明显的本机资源耗尽；无法回溯排除每一个超时时刻的短暂资源压力。
没有依据把升级电脑列为第一解决手段。

## 处理顺序与验证标准

1. **先控制上下文增长。** 完整规范首次按要求读取，后续复用结论和索引；读取长计划、历史和报告时
   使用相关段落、差异和摘要。完整检查结果继续落盘，回传只带结论和失败位置；图片按当前待验证
   问题选取关键帧，保持验收覆盖。此举减少重复信息，不降低内容验收要求。
2. **为阶段切换保留可接续状态。** 在原会话明显膨胀前，将完成项、待修问题和下一条命令写入现有
   PLAN/恢复记录。换新会话时避免重新读入全部历史，否则本次已经证明约 24 分钟就能再次接近上限。
3. **再做网络对照。** 相同电脑、版本、账号、模型、推理强度和输入，比较当前代理与已知可用的另一
   条代理线路；保持工作负载一致。记录请求启动、首个事件、最后事件、完成或错误，而不是只测网页。
   当前没有取得第二条线路的同条件结果，因此还不能宣判具体节点。
4. **最后做跨机对照。** tb24/tb26 使用相同版本、账号、模型、输入规模、传输方式和出口。若条件
   不同，分别记录，不能把所有差异归为硬件。tb26 的具体 bot/会话与日志仍待取得。

自动压缩阈值可以作为后续单变量试验：较低阈值使每次压缩处理更少历史，但也会增加压缩次数，
净效果需实测。不能把“调低阈值”“关闭 WebSocket”“延长超时”任何一项直接承诺为根治。
看门狗属于故障后的恢复层，无法修好远端流或链路；相关恢复缺口另见 RESEARCH-040。

本轮只做取证与只读探测，未修改生产代理、模型、全局配置或 VoiceOver 的制作文件。

## 来源与复核入口

- 本地会话：由 effective registry 的 `cxp` home 和 `bridge-codex-app-ready-tb24-voiceover.json`
  绑定 thread，读取对应 rollout 的 `task_complete`、`compacted` 和 token 用量。
- 运行日志：`cxp` home 的 `logs_2.sqlite`，只读查询指定 thread 的 `codex_core::responses_retry`、
  `codex_core::client` 和 HTTP 元数据；不展示凭据、请求正文或隐藏推理。
- [OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)：自动压缩阈值可配置；
  SSE idle 默认 300,000 毫秒，流中断重试默认 5 次。这是文档默认值，现场压缩重试以日志中的
  `max_retries=2` 为准，不能混用两种计数。
- [OpenAI Compaction 文档](https://developers.openai.com/api/docs/guides/compaction)：压缩用于缩小
  长会话上下文，保留后续所需状态；请求规模也是延迟管理的一部分。文档不能替代本次链路故障归因。
