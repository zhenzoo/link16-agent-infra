# 跨仓主动工作台的分派与审阅

## 总体样式

工作台上方是连续编号的业务表，下方是项目日轴。每笔审批占业务表一行，沿用业务序号。四列分别显示序号与登记执行者、业务与交付物、实际结果、附件。新业务置顶，缺结果留白。侧栏保留业务审批、项目时间线，更新时间在标题上方。

## 一个主号对接本人

本人指定的主号负责收件、排序、派单、追单、收结论、更新工作台和按授权发送消息。每项业务由原单指名的执行者查看原件、实施和验收。独立复核者只读原件，产品作者继续持有整件的写入及消息职责，主号始终只收结论和同版预览。接入新仓时登记来源项目、资料入口、执行者、可写范围和业务验收范例。按业务类目在本文件维护成品标准；岗位、资料入口和授权名单由各业务登记。原件、凭据和私聊记录按原访问范围保管。

## 何时独立开工

先写明谁在什么时候等哪件成果，再看任务间有没有依赖。临近评审或阻塞他人开工列 P0，需本周交付列 P1，可顺延的小事列 P2。明天同一场评审要看两份可独立编写的文稿，两名作者可以同时开工；多笔短报销由一人逐笔预填。计算、建模和渲染派到具备相应软件与性能的机器。同一物品或事项从模型、文稿、录屏/GIF、回填、自验到获准的消息统一交一名责任人，不同物品可并行。产品发布者只上架经该作者验收的同版成品。转手前收原作者停笔与封存交接回执，关联在途单并撤销旧作者的写入/外发职责。已经有人接手的任务沿原单跟进；空闲、掉线和完成要用现场状态或成品区分。

## 派单保留原话

本人明确给出的要求、示例和质量纠正按原顺序逐字交给最终执行者，保留段落、数字、否定项与附件指引。主号另起一段补上缺少的原件、改前基线、谁能写什么、验收方法和回传对象。换会话、上下文压缩或跨机中转后，按原消息标识找回正文再交接。动手前留存本项 Git 基线；验收提交只纳入本项。执行中已有新纠正，补到同一单，只续做未交的部分。

## 看成果与判断闭环

人员实名以同一组织的通讯录或本机已核实的名册为准。语音转写中的人名只作检索线索。遇到同音或重名，结合账号、部门或原会话核对；身份仍不明时保留待核。工作台和归档用实名；发消息用本人指定或在本人私聊中用过的称呼。已发原文按原样留存。

### 文档、模型与演示

单件 HTML 演示用「本地 · 成品名」「在线 · 成品名」两个入口，绑定同一交付物。打开应到同一章或演示首页。训练候选、单窗回放、验证材料随演示查阅。私有手机工作台按「本地」展开可复制的桌面原件路径。交付物本身是图或 GIF 时直接展示。提案沿用原表，高亮拟改行。

规格逐项写用途、功能、定义、材料、数值和单位。设计延续原 FreeCAD 工程，从原机位出图、录动作并放回对应功能行。核实际装载、接触与运动。图纸选项和生产规格分开。比较用同一组列，一张文档统一一个可操作入口。

### 消息与配件采购

称呼沿用本人原私聊。采购稿首行称呼，随后分行列需求与量档、现有方案、请求动作。日期、数量与所请报价单位写在一起。附直接需求入口，写清谁谈价、谁拉群；另一物品独立核数量和经办人。出处在业务原单留存。对方表示收到只闭环联络，审图或批准另记。本人给定的逐字配文按原单发送；本人接手的联系人退出代发队列。首次称呼取本人或通讯录已核的名字，具体名单保存在私有登记。

采购草稿的可调限值为 2–6 个非空信息行，每行最多 52 字，信息点合计最多 160 字，完整 HTTPS 链接计 4 字。每项采购登记必须出现的信息点及其等价写法。已发消息保留原文。普通回复沿用自然表达。

### 审批、周报与日程

报销先核同类历史实例及原 Excel，分别登记预订、本人实付、发票和提交。周报按原单元格核本人手写进展、成品、负责人、承诺和日期，写回前先合并新手改。晨间默认发消息跟进；约会依本人交办核参会人、忙闲、房间及最终名单。

每笔审批单独一行。已有实例链接定位到具体实例。已保存草稿优先用本人从工作台独立点开并读回内容的链接。飞书只支持从原表草稿箱重开时，结果格只给该原表一个链接，标签列草稿箱、保存日期时间和编辑入口。用同一草稿保存前与退出重开的回执核对。审批填表和重开核验执行 [审批草稿 SOP](SOP-151-approval-draft.md)。

项目日轴每屏约七天，可横向跨周、跨月。本人确认、原回复解决问题或执行者按原单验收交付后，按真实日期、项目轨、来源和事项去重登记。同日节点向下排列，名称完整可读；点击查看来源与原件。轨道使用窄色条，同机型同色，机型组间距至少 18 px。节点省略类别、重复机型；初版标 V1.0，其余版本沿用原件。仅知月或区间时覆盖实际范围。

每行登记一条消息、一份文件或一笔审批。同一文件的本地和在线入口合计一份；多名收件人、多笔审批各占一行，保留原业务责任人。已发消息定位原聊的具体一条，待发稿核收件人及完整原文。截图、回执、测量记录和动图留在对应原件。工作台自身也登记固定入口。本机渲染和手机包均校验全表顺序、作者、类型、数量与目标，错一项即阻止发布。

## 怎么增加一项可验证规则

先选业务类型与触发动作，再写输入、通过条件、正例、必失败反例和需要人判断的部分。生成前校验数据，发布前再校验呈现，发消息或回复时校验最终正文。错误应能指出问题字段。更新规则时将真实入口与反例接入同一函数。字数、字段和入口可以机械判；价格是否准确、对方是否批准须核原单。执行入口见 [SOP-150](SOP-150-proactive-agent-loop.md#workbench-checks)。

## 谁在何时汇报

执行者沿原单交结果、验收结论、同版预览和剩余限制；受阻就交直接缺项、保存位置及恢复条件。主号将回执关联原单，缺证据时追原执行者或另派复核，随后更新条目。给本人只发一张按结果编号的私聊交互卡，每点之间空一行，直接给结论、能量化的指标、预览和待拍板项。过程留在原单。

每天 09:00（上海时间）的巡检用于查漏和更新工作台；当天验收通过的成品当时汇报。执行者回主号、主号向本人交付是两次投递。区分“执行者已回”“成品已验”和“本人私聊已送达”；最后一项以正确私聊中能回读的卡片为据。具体命令与失败恢复见[主动工作流程](SOP-150-proactive-agent-loop.md)。
