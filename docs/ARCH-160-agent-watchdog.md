# ARCH-160 · 看门狗

## 1. 它是什么

**一个 Python 脚本**：`feishu/bridge_watchdog.py`，形态与 `feishu/bridge_cron.py` 完全一致
（单文件 + `run` / `start` / `stop` / `status`，另加一个手动 `failover`）。

它每 120 秒扫一遍 **wmux 全部 workspace 的全部面板**，认出「这个会话中断了」，然后按中断类型采取不同动作。

**覆盖对象一视同仁**：`xhs-card-gen` / `voiceover` / `pressroom` / `notes` …… 在它眼里都只是
「一个 session agent」，没有谁特殊。拓扑来自 `workspace.list` 实时查询，**零硬编码 bot 名单**，
bot 增减自动跟随。

## 2. 一个循环 + 一张规则表

要支持一种新的中断类型，**就在这张表里加一行**。

| # | 判据 | 动作 | 为什么 |
|---|---|---|---|
| **R3** | 停在交互 picker（AskUserQuestion 等） | **什么都不做** | 它在等主人回答，不是卡死。往那儿注回车会**替主人乱选一个答案** |
| **R2** | 屏命中限流签名 **且** 该账号额度判定=满 **且** 连续 2 轮静止 | 换号 + 把原任务交接给新会话（见 §4） | 会话死在这儿不会自己好，等到额度重置可能是几天后 |
| **R1** | 屏有 `API Error:` / `API Error (` 或错误类型码，**且没在 retry**，且连续 2 轮静止 | 往面板注一句「继续」 | 网络/服务抖动，推一下就能从上次停的地方接着做 |
| **R5** | Codex 的 rollout 里，**最后一个回合以 `task_complete{error}` 收尾**、后面没有新回合（限流除外） | 告警 + 注「继续推进」；连着 3 个回合都被掐 → **停手，只告警** | 回合被服务端掐断后**没有任何东西会再踢它一脚**（见 §3.5） |
| **R4** | 桥进程 活→死 | 告警（仍走 DM·挑名册里第一个能解析出目标的 bot 代发） | 2026-08-30 实测推翻了「桥挂了 DM 发不出」：`send_feishu_msg.py` 直连飞书 REST、不经过桥进程（停掉 tb24-notes-3 的桥后仍 ✅ 已发）。webhook 的最后一条理由消失，随全部兜底一起拆除 |
| **R6** | `_state/bridge-hwm-corrupt-<bot>.log` 出现【新增】行 | 告警（状态类·30min 冷却·记 `seen` 水位不重报） | 断电会把没落盘的水位书签变成全 NUL。`load_hwm` 已 fail-closed 自动修好（不重放历史），但这意味着①机器崩过②崩溃前最后一批未送达的消息被跳过（仍在 outbox 可捞回）。**这条日志此前只有写入方、没有读取方**——2026-08-30 洪水就是这个形状，42 分钟无人知晓 |

规则**按顺序匹配，先命中先处理**。任一轮里 wmux RPC 不通、或某块屏读不到 → **本轮跳过，绝不据此动手**。

## 3. 三道防护闸（改判据前必须读懂）

这三样都是踩过坑才有的，**一行都别改**：

1. **防误判** —— 只认 Claude **自己渲染**的错误签名（`API Error:` / `API Error (` + 少量错误类型码），
   **不认正文里的话题词**。2026-06-18 实证：旧版用 `rate limited` / `overloaded` 这类广义词扫屏，
   正在写 AI 内容的 worker 正文含这些词就被误判成卡死、被注「继续」打断 ——
   **读屏无法区分「正文提到」和「真报错」**，只能靠结构化签名。
2. **防抢跑** —— 屏上有 `retrying` / `attempt ` / `esc to interrupt` 等 = Claude 自己在重试、会自愈 → **绝不碰**。
3. **防自激** —— 注入的文本本身**不含任何错误签名**（见 `NUDGE_TEXT`），
   否则下一轮读回屏幕会把自己的注入当成错误，无限循环。

外加两道节流：**同一面板两次注入至少隔 10 分钟**；**「带错 + 静止」连续 2 轮**才动手。

> 这三道闸各有一个单测，且 `tests/mutate_bridge_watchdog.py` 会**把它们逐个改坏、验证对应用例变红**。
> **没有变异测试的绿灯不算数** —— 架构类的东西看不见，一排绿灯既可能是闸在守，也可能是用例没咬合。

## 3.5 R5 · Codex 回合被服务端掐断（唯一一条**不读屏**的规则）

**立项现场（2026-08-25 `tb24-voiceover`，静默烧掉 17 小时 18 分）**：

| 北京时间 | 发生了什么 |
|---|---|
| 08-25 07:51:02 | Codex 把答复写完了（rollout 里躺着完整的 `agent_message`） |
| 08-25 07:51:04 | 紧接着的续跑请求被 OpenAI 判成 `invalid_prompt`（"your prompt was flagged as potentially violating our usage policy"），这一轮以 `task_complete{error, last_agent_message: null}` 收尾 |
| 08-25 07:51 → 15:43 | **7 小时 52 分零推进**，主人零通知 |
| 08-25 15:43 / 15:45 / 15:47 | 主人三次手动追问，**每一次都被同一个分类器拦下** |
| 08-25 15:47 → 08-26 01:12 | **又 9 小时 25 分零推进**，之后才自己恢复 |

**为什么全套东西同时失明**（两处断，缺一都不至于这么久）：

- 桥只在 `final` 事件上回传 → 这一轮压根没有 `final` ⇒ **主人在飞书上一个字都没收到**，
  界面上和「它正在埋头干活」完全一样；
- 看门狗 R1 只认 `API Error:`、R2 只认限流横幅，**这个错谁都不认** ⇒ 当天日志 `本轮动作 0`，一整天。

**不是我们的 prompt 有问题**：`openai/codex` #39745 / #40327 / #7250 同期大量同形报告
（"in the middle of Codex working on its own, with no human input"），服务端分类器误伤，
Codex 客户端自己也没把它当可恢复错误处理。**所以这事只能在我们这一层兜。**

**为什么这条判据不读屏**（和 R1/R2 反着来，是有意的）：
这个错的屏幕文本是一句大白话（`your prompt was flagged…`），**正文可以原样出现**——
写下这条规则的当天，主人就把这句话原文贴进了另一个 bot 的会话里。
2026-06-18 那条老教训（读屏分不清「正文提到」和「真报错」）在这儿是**加倍**成立的。
判据改读 **Codex 自己写的 rollout JSONL 里的 `task_complete.error`** ——
结构化字段、**只有 Codex 自己会写**，正文再怎么提也伪造不出来。顺带白拿两样：
「现在到底有没有在跑」（后面有没有更新的 `task_started`）+ 精确到秒的断点时间。

**四种情况一律不动手**：回合还在跑（最后是 `task_started`）· 主人自己按了中断（`turn_aborted`）·
正常收尾（`error` 为空）· 错的是限流（那是 R2 的双源判定 + 换号，别抢）。
⇒ **结构上不可能打断正在跑的活**，比 R1 的 `RETRY_MARKERS` 更硬。

**升级梯度**：前 3 个被掐的回合每个注一次「继续推进」（沿用 10 分钟注入冷却）并发 DM；
第 4 个开始**停手**，改发「我不再自动重推了，建议 `/handoff` 换全新 context」——
因为主人当天实测连续三次重推全被拦，**再推也是白撞**。停手之后**绝不静默**。

**thread 怎么认**：读桥自己落的 `bridge-codex-app-{thread,ready}-<bot>.json` 的 `thread_id`，
再到 `<codex_home>/sessions/**/rollout-*-<thread>.jsonl`。**认不出就返回「认不出」并计进心跳行**
（`R5 覆盖 n/m 个 codex bot`）——绝不改用「同 cwd 最新的那个 rollout」去猜，
同一个 cwd 上可能挂着好几个 bot，猜错就是把别人的故障记在这个 bot 头上。

## 4. 撞额度上限时发生什么

**判据是双源的**：屏答「是哪个面板撞的」，额度 API 答「这个号是不是真满了」，**两个都成立才动手**。
只读屏不够（屏会滚，那句提示会被挤出 25 行读窗）；只读 API 也不够（一个号可能挂着好几个 bot，有的在跑有的闲着）。

额度真源 = `feishu/agent_quota.py`，**打实时接口**：
Claude 走 `api.anthropic.com/api/oauth/usage`（国内直连、强制绕代理），
Codex 走 `chatgpt.com/backend-api/codex/usage`（走 `.env` 的 `PROXY_URL`）。

> ⚠️ **绝不读本地缓存**（`~/.claude*/.claude.json` 的 `cachedUsageUtilization`）：
> 2026-08-20 实测那份缓存停在四天前，会把 weekly=**100%** 的号报成 **0%** ——
> 误判方向恰好是最危险的那个（把满号当空号切过去，一切就再撞一次）。

换号八步，第 3 步之后每一步失败都发 DM 喊人、绝不静默：

1. 选号（排除刚撞的 → 同 runtime 优先 → 余量大优先；**「问不到」的号绝不选**）
2. 过闸（连续 2 轮静止 · 该 bot 24h 内自动换号 < 2 次）
3. **交接包快照**（必须在关会话之前——关了会话记录就没了）
4. DM 播报「要切了」
5. 写名册 `agent_runtime.persist_account`
6. 关旧会话 `wmux_session.close`
7. **重启该 bot 的桥进程**（`stop --bot X` → `start --bot X`）
8. 新号冷启 + 注入接手 prompt + DM 播报结果

> 🔑 **第 7 步为什么不能省**：`/account` 的处理里有一步是改**桥进程内存里**的 bot 字典。
> 外部进程改得了名册文件、**改不了别人进程的内存**。只写文件的话当时看着是好的，
> 等这个会话一死、桥要冷启时，它仍会用**旧 profile** —— 静默切回老号，且没有任何报错。

**交接包**（`feishu/_state/watchdog-handoff-<bot>.json`）从
`bridge-session-<bot>.json` 直接取 transcript 路径 / session id / cwd / profile——比读屏准，
也不需要满机器搜。再加一份「上个会话可能留下的在途工作」：**进程 + 最近改动文件双探针**。

> ⚠️ 两个探针**都不完整，所以都报**：进程探针只能匹配命令行，`nohup bash scripts/xxx.sh &`
> 这种相对路径起的孤儿匹配不到（父进程已死，树遍历也找不到）；文件探针（项目目录下最近 6 小时的
> mtime）补这块。且必须带 **CPU 与 mtime 两个佐证** —— 2026-08-20 实测 voiceover 有 4 对 render
> shell 还挂着，**光看进程会以为在干活**，但每个只烧了 5-28 秒 CPU（真渲染要烧 ~1669 秒），
> 日志两小时没长 ⇒ 其实是卡死的孤儿。**结论完全相反。**

接手 prompt 明确规定读法：**禁止通读 transcript**（那份可能上百 MB，通读会把新号也撑爆
= 用一次限流换来另一次限流），先读尾部定位再按需回溯；并写死「不需要跟我确认、不需要对齐、直接接着推」。


## 4.5 两版接手 prompt：口径**刻意相反**，别统一

同一套交接包（`snapshot_handoff`）喂给两个不同的 prompt，服务两种相反的处境：

| | `build_handoff_prompt` | `build_align_prompt` |
|---|---|---|
| 谁触发 | **看门狗自动**换号（撞额度上限） | **主人手动** `/handoff` |
| 主人在不在场 | **不在**（半夜撞限流） | **在**（他正要开新东西） |
| 结尾指令 | 「**不需要跟我确认、直接接着推进**」 | 「**汇报完就停下等我**」 |
| 为什么 | 会话必须自己活下去，等人等不起 | 新会话**还不知道主人要什么** —— 猜是最坏的选择 |

> ⚠️ **别把这两版「统一」成一个。** 它们的差别不是措辞，是**主人在不在场**。
> `tests/test_bridge_watchdog.py::test_两版prompt口径必须相反` 守着这条。

`/handoff` 与 `/close` 的三处差别（缺一不可，见 `feishu_bridge.py` 的 handler）：
① **不切账号、不回默认目录**（你只是要换个干净 context，不是换号搬家）
② **关会话之前先快照交接包** —— 关了就没了，顺序不能反
③ **主动起新会话并注入**（不像 `/close` 那样等下一条消息才懒启动）

## 5. 生命周期：绑桥，不绑任何业务仓

**桥起了 → 看门狗必定在。** 它随 `feishu_bridge.py` 的**整体** `start` / `stop` 起停
（`start --bot X` 单起某个 bot **不会**带起它——它是全机级的，每次单起都多拉一个就成灾了）。

> **它没有自己的计划任务，这是有意的。** 桥的自启脚本本来就是探测式的（多个候选路径 `Test-Path`），
> 所以看门狗**根本不需要知道自己装在哪** —— 跨机的路径问题从源头消失。
> 旧的 `AutopilotWatchdog-Autostart` 正是因为写死路径，2026-08-17 在 TB25 装不上
> （`Test-Path` 返 False、注册不下去）；2026-08-20 已 **Disable**（未 Unregister，可随时回滚）。

单实例：`start` 先顶掉同名残留再起，与 `bridge_cron.py` 一致。日志 `feishu/_logs/watchdog.log`。

## 6. 告警走哪条路

| 事件 | 通道 | 为什么 |
|---|---|---|
| 撞限流 / 已换号 / 已接手 / 换不了 / 已注「继续」 | **该 bot 自己的飞书 DM**（`send_feishu_msg.py`） | 用哪个 bot 发，就等于说明是哪条线，主人不用猜 |
| 回合被服务端掐断（`policy_nudged`）/ 连掐 3 次已停手（`policy_stuck`） | 同上 | 掐断时**桥没有 final 可回传**，DM 里除了看门狗这条什么都不会有 |
| 桥进程死了 | **同上**（`_notify_bridge_down()` 挑第一个能解析出目标的 bot 代发） | 「桥挂了 DM 发不出」是错的——发 DM 不经过桥进程，2026-08-30 停桥实测仍能送达 |
| 水位书签损坏（`hwm_corrupt`） | **该 bot 自己的 DM** | 谁的水位坏了就用谁的线报，主人不用猜 |

状态类告警（撞限流、`policy_stuck`）每 bot **30 分钟**最多一条；
动作类（换号成功、`policy_nudged` 等）**必发不吞**。

> 🩸 **本部件的立项起因就是这条**：旧看门狗的告警走的是飞书自定义机器人 webhook（另一个群），
> **主人在与 bot 的 DM 里什么都看不到**。2026-08-20 `tb24-voiceover` 撞限流停了两小时无人知晓。
> 那不是坏了，是设计如此 —— 所以这条通道必须换。
>
> **2026-08-30 走完最后一步：webhook 整条拆除，不再保留任何「发不出就改投别处」的兜底。**
> 主人的判据：兜底给失败开了一条特殊通道，让「没送到」长得像「送到了」。三次同形状事故都是它
> （taoci-7 刷群 767 条 / 2026-07-06 已砍掉瞬时错那半 / 8-30 洪水时医生朝着早被关键词校验
> 拒收 748 次的群喇叭喊「需人工」，主人 42 分钟一无所知）。DM 发不到主人自己会察觉，
> 届时他直接找 link16 或上机器看 —— 与其多一条会静默失效的通道，不如让失败就是失败。

## 7. 怎么看它在干嘛

```
python feishu/bridge_watchdog.py status [--verbose]
```

必报三样：**在看护几个面板** · **上次巡检什么时候** · **注入记录**，
外加一段跨机自检（本机找不找得到 wmux / 真名册 / 桥）——**换台机器一跑就知道能不能用**。

手动换号（破坏性 · 建议先预演）：

```
python feishu/bridge_watchdog.py failover --bot <bot> [--to ccp] [--dry-run]
```

## 8. 与 xhs `_autopilot/watchdog.py` 的关系

那个文件**只剩两件事**，都读 xhs 自己的产物：整条线卡死检测（`posts/` 六个目录 mtime）、
写帖里程碑播报（Stage E + 封面卡）。它由 xhs 巡航自己管，**本部件完全不感知它**；
反过来，xhs 没起时全机保活照常。

> 历史坑（值得记住的失效形状）：那份文件当年读 `_autopilot/bridge-session-*.json` 认 bot 名，
> 2026-06-27 桥迁进 Link16 后那份名册就冻结了，2026-08-20 实测**命中活面板 0/7**。
> 它**照常报警、日志照常在写**，只有「是哪条 bot 线」一直是错的，**且没有任何报错**。
> 更隐蔽的是 picker 识别的结构化那条路因此永久短路，只剩读屏兜底 ——
> 而结构化那路存在的唯一理由，就是「免疫高 picker 把页脚挤出读窗」。
> **进程活着、日志在写、告警在发，唯独内容是错的** —— 本仓最常见的故障形状。
