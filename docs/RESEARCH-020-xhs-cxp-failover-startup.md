# tb24-xhs-autopilot 切到 cxp 失败调查

调查对象是 **2026-09-06 凌晨 04:33–04:37** 的事件。下文时间均为北京时间。

## 结论

**cxp 账号、模型请求和 app-server 启动已经成功，失败发生在后面的远程终端接入。**
Codex 在 04:34:41 已返回 `LINK16_APP_SERVER_READY`，04:34:42 完成探针回合并接上观察进程。
随后终端在 04:34:43 请求检查目录信任，没有进入终端自己的 `thread/resume`。

已用事发相同版本 **Codex 0.153.4**、当前 cxp 配置、相同 XHS 目录复现两个相互叠加的缺口：

1. Link16 将目录信任键全部改成小写；Codex 远程终端的配置查询按字符串原样查键。
   XHS 的小写记录存在且为 `trusted`，原样大小写记录不存在，仍弹出目录确认框。
2. 确认框位于终端顶部；桥的启动轮询只读末尾 **30 行**。在 **45 行**的终端中，这 30 行全是空白，
   自动确认和就绪判断都不会触发。等待时间增加并不能使这个静态界面自己消失。

停工扩大为数小时的原因也已确认：**换号先关闭整个旧工作区，再尝试启动新会话；新启动失败后只发告警并返回，
没有持久的接管重试任务。**旧工作区里的总控、radar、P266 writer 三个面板在同一秒被关闭。

证据边界：原失败截图在上午重新成功启动后已被清除，旧 PTY 缓冲也随关闭删除。
所以不能直接证明事发 PTY 的准确行数；“45 行导致末尾读窗漏掉确认框”是本机无头实测，
与当时的请求停点以及本机现有全尺寸面板的 45 行高度吻合。原日志、模型探针成功、面板关闭和交接未投递均有直接记录。

## 启动成功与终端失败为什么能同时发生

启动顺序见 [codex_app_server_worker.py](../feishu/codex_app_server_worker.py)：

`app-server 监听 → thread/start → 模型探针完成 → observer 接入 → 启动 --remote 终端 → 桥读屏判就绪 → 投递交接任务`

模型探针只证明后端能工作。终端仍有自己的目录信任确认；它尚未接入，就不会接受 P266 的交接任务。
这次原始 rollout 只有探针，没有业务提示词，也没有接管后继续写帖的回合。

对应线程：`01a07347-94f2-7cb1-9324-b1e7c6f509c1`。
原 rollout 位于 cxp 的 registry home 下：
`sessions/2026/09/06/rollout-2026-09-06T04-34-26-01a07347-94f2-7cb1-9324-b1e7c6f509c1.jsonl`。

## 可复现证据

本次诊断通过 Link16 的 `agent_profile_cli.py run --profile cxp` 启动独立诊断进程。
终端由无头 ConPTY 承载；没有创建新的 wmux 工作区，没有发送业务消息，没有启动新的模型回合。
每次诊断前后检查 cxp `config.toml` 的 SHA-256，均相同；诊断子进程已清理。

### 1. 原生配置查询

`config/read` 返回的 XHS 信任项只有小写路径。查询原样大小写路径时，精确匹配为空；查询小写字符串时匹配 `trusted`。
对照目录 tennis-post 和 Link16 已有原样大小写信任项，精确匹配通过。
配置查询本身并不调用模型。

Codex 0.153.4 的实现确实使用 `projects.get(trust_target)`，没有在这一处折叠 Windows 大小写：
[官方版本源码：read_remote_project_trust](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/config_update.rs)。
Link16 的 [ensure_codex_trust](../feishu/agent_runtime.py) 则将键转成 `.lower()`，并用大小写不敏感的文本检查判定“已经存在”。
这两种判断不一致。

### 2. 真实终端、45 行对照

在 128 列 × 45 行的原生远程终端里，实际出现目录确认框：

- 完整屏幕：桥的 `needs_trust_confirmation` 返回 `True`；
- 同一屏幕的末尾 30 行：全空白，返回 `False`；
- 完整屏幕的 `is_ready` 返回 `False`，不会把确认菜单当可接收任务的界面。

因此问题在 [feishu_bridge.py](../feishu/feishu_bridge.py) 的启动观察范围：
`_wait_agent_ready` 调用默认 `read_screen(pty)`，默认值为 30；到失败取证时才扩大为 100 行。
“失败时能看见，等待时看不见”可解释告警为什么一直等满 150 秒。

### 3. 两个没有修好的快捷尝试

- 只给诊断 app-server 加启动参数 `-c projects.…trust_level=trusted`，终端仍停在目录确认。
  不能将启动参数覆盖当成本问题已经修好。
- 只将启动目录字符串改成全小写，远程路径解析会将盘符改回大写，仍不精确匹配配置中的全小写键，终端仍停在确认框。

这两组均保持生产配置不变。修复建议必须回到原生信任记录与启动界面观察本身，而不是宣称加一个参数就能解决。

## 停工被放大的三处设计问题

### 整个工作区先关，新会话后验

[bridge_watchdog.py 的 failover](../feishu/bridge_watchdog.py) 在新会话验收前调用
`wmux_session.close(rec["workspace_id"])`。该函数关闭整个工作区，因此总控之外的 writer 也被关闭。
本次不是“可能会影响 writer”：wmux 日志直接记录了三个 PTY 在 04:34:11 被关闭。

交接包保存了总控 transcript 与后台进程/文件线索，但没有完整列出每个子面板的 session/thread 绑定。
文件已经写到磁盘的部分仍在；“关闭面板”也不等于删除 Claude 历史归档。损失主要是运行连续性和自动恢复入口。

### 启动失败之后没有待恢复任务

`ensure_session` 抛异常后，`failover` 发告警并 `return False`。
保存下来的 handoff JSON 不是一条带 pending/claimed/delivered 状态的重试队列。
守护循环从仍存在的面板出发，没有扫描这类“面板已关、任务还没交出去”的失败接管。
因此账户恢复、时间过去或看门狗继续心跳，都不会自动完成这次交接。

### 失败现场会被下次成功清掉

`_finish_worker_startup` 成功就调用 `_clear_startup_failure`。
所以 `/screen` 的“失败现场已保存”仅在下一次成功启动前成立，无法承担事后审计。
本次 14:12 的新 ccp 会话成功后，原失败记录已不存在；`.write.lck` 还在不表示内容还在。

## 其他发现与排除

- **限额告警口径写错了维度。**原屏幕是 session limit，恢复 06:10；告警固定展示 weekly 使用 30% 和 weekly reset 09-07 22:59。
  这让“周额度只有 30% 为什么就满了”看起来矛盾。选号判定使用 session/weekly 的较高值，显示模板却只打印 weekly。
- **不是 cxp 额度不够或登录失败。**原探针成功，原 token_count 记录周使用 64%。
- **不是整段外网不可用。**原模型完成响应，终端也已连到本机 app-server。
- **GitHub 更新检查的 403 不是这次接管失败的充分原因。**那条错误属于 TUI 查询最新版本；原生无头复现明确停在目录确认。
- **不是 P266 交接提示词太长。**它尚未注入；原线程只有启动探针。
- **不是 R6 未定义变量再次打断换号。**03:13 后的守护进程已替换旧版本，04:34 换号确实推进到了新终端；更早的 R6 错误属于另一段运行历史。
- 同日上午 tb24-link16 的第一次 cxp 启动也出现相同“探针成功→终端 trust-read→150 秒超时”的日志形状，说明问题不限于 XHS 业务。

## 建议修复顺序与验收

本次交付为调查结果，**未重启生产桥、未修改生产信任配置或自动换号代码**。

1. **对齐信任键与原生远程终端的实际路径。**保留已有 trust/untrusted 决策，按原生解析后的路径精确落键；不要只做字符串小写化或用 `-c` 宣称修好。
   验收必须覆盖 Windows 路径大小写、盘符归一化、有无项目 `.codex`、显式 untrusted，且真实 remote TUI 无确认阻塞。
2. **启动判断读取完整可见屏，保留确认菜单的语义识别。**不能因为末尾 30 行为空就认为没有确认框；也不能对所有弹窗盲按回车。
   验收用真实 24/45/60 行终端，并保证未知菜单仍不自动接受。
3. **让新会话验收成功之后再处置旧会话。**至少精确保护其他子面板，或先保存全部子面板的恢复绑定；新号失败时业务现场应可恢复。
   验收需要三面板工作区、新号失败以及新号成功三种场景。
4. **给失败交接增加持久状态与有界重试。**记录尚未投递、等待重试、取消、已投递；用户 `/close`、切号或新任务到来时有明确取消/接管规则。
   验收要证明重启看门狗后仍能续接，同时不会重复投递或复活已取消的旧任务。
5. **按尝试保存失败证据，并按真实触发维度报告限额。**新成功不删除旧失败快照；session limit 的告警应显示对应 session reset。

修复跨越目录信任、终端启动、工作区生命周期与恢复状态，不应只把 150 秒改长后宣布完成。
