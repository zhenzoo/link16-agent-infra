# PLAN-931 · 看门狗独立成 Link16 常驻部件

> 立项 2026-08-19（align 四段走完 · 主人拍板）。
> **前置事实**：本 plan 由一次「黑窗排查」牵出——排查中发现看门狗放错仓、且有一个接口已静默失效两个月。

## 0. 立项背景与交付契约

### 0.1 为什么要动

`xhs-card-gen/_autopilot/watchdog.py`（691 行 / 31 函数 / 37 KB）其实是**两个东西被捆在一个文件里**：

1. **全机 agent 保活器**（通用）：扫全机所有 wmux workspace 的所有面板，发现 agent 卡在
   API error / 限流 / 断连且没在自愈 → 注一句「继续」把它推走。**这是 Link16 层的基础设施**，
   与写小红书帖子毫无关系。
2. **写帖巡航监工**（xhs 专属）：盯 xhs 内容目录的 mtime 判断整条线是否停滞、发布页铺好后
   发飞书 + 封面卡。

放错仓已经造成**真实腐烂**（非理论风险，2026-08-19 实测）：

| | 看门狗读的 | 桥实际写的 |
|---|---|---|
| bot 名册 | `xhs-card-gen/_autopilot/bridge-session-*.json`（7 个 · **冻结在 2026-06-27**） | `link16-agent-infra/feishu/_state/bridge-session-*.json`（21 个 · 活的） |
| arch 线 pty | `daemon-060b56bb`（陈旧） | `daemon-0f268f18`（真值） |

2026-06-27 桥从 xhs 迁入 Link16 那天，看门狗这个接口就断了。**它这两个月照常报警，但「是哪条 bot 线卡了」一直标错。**
这是本仓「尺子坏了但输出正常」的又一个实例：进程活着、日志在写、告警在发，唯独内容是错的。

### 0.2 主人拍板的五条约束（2026-08-19 · 不可推翻）

1. **形态**：不做飞书 skill，也**不是「模块 + CLI」两个东西**——**就是一个 Python 脚本**，
   形态与 `feishu/bridge_cron.py` 一模一样：**单文件 + `run/start/stop/status` 子命令**，起它就完了。
   （主人 2026-08-19 明确纠正：别搞复杂，原来什么形态就什么形态。）
2. **生命周期绑桥、不绑 xhs**：电脑开着 + 桥起了 → 看门狗必定在。xhs 没起，它只是不推写帖那条线，全机保活照常。
3. **xhs 侧留成瘦客户端**：职责2/3 留在 xhs，通用能力向 Link16 取。
   **发群消息那部分主人认为已不需要，但本次不动**——瘦身是独立一件事，不混做。
4. **中英文自动**：不让用户配置，**由系统检测该 session 上下文语言**，中文 session 发中文、英文 session 发英文。
5. **evaluation 是本次推进的评分体系**，不是给看门狗写回归测试。要建立「到底怎么样算做完、算做好」的机制，
   并用它判定每个 stage 的推进质量。

## S1 · 先建评分体系（evaluation harness） — [x] 2026-08-19 完成

> **为什么排第一**：align §4「能读数据的 infra 先造」。评分体系不先建，后面每一步都无法判定
> 「做好了没」，只能靠感觉——那正是主人这次点名要消灭的东西。

### S1.1 定义「做完 / 做好」的判据维度
1. **解决什么问题**：现在判断一步是否完成，靠的是我口头说「改完了」，主人无法独立核验。
2. **矛盾点**：判据太松 = 等于没有；太严 = 每步都卡住不能推进。且「做完」（功能在）与
   「做好」（没留债）是两件事，混成一个分数会互相掩盖。
3. **推荐方案**：**拆成两组分数**——`完成度`（功能性判据，二值：接口通没通、进程起没起、
   测试过没过）与 `质量度`（回归 / 净增 / 文档 / 可观测性，分档）。两组分别算分、都过线才算该 stage 完成。
   这样「功能跑通但留一堆债」不会被一个高分掩盖。
4. **改什么·改哪里**：本步只产出判据定义，写进本文件 S1.1 附表（不写代码）。
5. **交付物**：一张「维度 / 判据 / 数据从哪来 / 满分条件」表，覆盖至少 6 个维度。
6. **验证**：每个维度都能指出**具体的数据来源**（某个文件、某条命令的输出、某个测试的 exit code）；
   凡是只能靠人主观判断的维度，要么改写成可测形式，要么剔除。

> **为什么分两组**：`完成度` 是二值的——功能在不在，没有中间态；`质量度` 是分档的——债留多少。
> 混成一个总分，会出现「功能全跑通但一身债」被高分掩盖。两组分别过线，才叫做完**且**做好。

### S1.2 实现评分器 `tests/eval_plan931.py`
1. **解决什么问题**：判据写在文档里不会自己跑，主人还是得信我。
2. **矛盾点**：评分器本身可能坏（尺子坏了、输出仍正常）——它必须能自证。
3. **推荐方案**：评分器每个维度返回 `(分数, 证据字符串)`，**证据必须是实测输出的片段**
   （文件路径 + 行号、命令 exit code、进程 pid），不允许只返回分数。再加一个 `--self-test`：
   故意喂错误状态，验证该维度确实会扣分——**尺子先验尺子**。
4. **改什么·改哪里**：新增 `tests/eval_plan931.py`；不进 pytest 默认套件（它是验收工具、不是单测）。
5. **交付物**：可跑的评分器，输出「总分 + 逐维度分 + 每维度证据」。
6. **验证**：`--self-test` 全绿；对当前未改动的仓库跑一次，分数必须**明显偏低**（否则说明判据没咬合）。

### S1.3 打基线分（before）
1. **解决什么问题**：没有 before 就没有 after 可比，「改好了」无从证明。
2. **矛盾点**：基线要在动任何代码之前打，一旦开始改就再也拿不到了。
3. **推荐方案**：S2 起第一行代码之前跑一次，结果**写进本文件**（不只留在终端）。
4. **改什么·改哪里**：本文件新增「基线分」小节。
5. **交付物**：一组带日期的基线分数 + 证据。
6. **验证**：基线里必须包含那条已知坏掉的接口（bot 名册读错仓）被扣分——如果它没被扣分，说明判据漏了。


**建尺子过程中尺子自己被打脸两次（记下来，免得重蹈）**：

1. `--self-test` 抓出 **Q1 是摆设**——「没找到多余配置文件 = 满分」，可空目录里本来就什么都找不到。
   修法：任何判据都要**先确认被评对象存在**，否则判 0（「什么都没有」≠「做得好」）。
2. 首次跑基线时 **C3 报「workspace.list 返回不是 JSON」，但那明明是合法 JSON**——真因是评分器的
   `_run()` 把输出截断到 400 字再拿去解析。C3 那次判 0 虽然结论对，**理由是假的**。
   修法：`_run()` 绝不截断，截断只允许发生在展示层。
3. 基线还暴露 **C3 判据本身设计错**——「名册命中率必须 100%」永远达不到（16 条名册里只有 6 个 bot
   真在 wmux 面板里跑）。改成**相对判据**：Link16 名册命中活面板数 >0 且严格优于 xhs 僵尸名册。

> 这三条都是同一个教训的不同形状：**下结论前先验测量工具**。评分体系本身若不可信，
> 后面所有 stage 的「做完做好」都是空话。

## S2 · 切分与接口契约 — [ ]

### S2.1 逐函数切分表（通用 vs xhs 专属）
1. **解决什么问题**：31 个函数混在一个文件里，凭印象搬会漏或搬错。
2. **矛盾点**：有些函数**两边都用**（如 `rpc` / `log` / `read_pane`）——搬走 xhs 会断，留下 Link16 会缺。
3. **推荐方案**：分**三类**而不是两类：`通用`（搬）/ `xhs 专属`（留）/ `共用底座`（搬进 Link16，
   xhs 侧改为经 CLI 调用）。第三类是这次真正的设计活。
4. **改什么·改哪里**：本文件新增切分表，31 行、每行标类别 + 依据。
5. **交付物**：31 个函数的完整归类表。
6. **验证**：三类数量相加 = 31；每个「共用底座」函数都写明 xhs 侧改用什么方式取。

### S2.2 CLI 接口契约（对齐 bridge_cron）
1. **解决什么问题**：主人明确要求「同一层级、同一套接口」，不能又发明一套动词。
2. **矛盾点**：看门狗比 cron 多一个「查它现在在看护谁」的需求，硬塞进 4 个动词会别扭。
3. **推荐方案**：**主动词严格对齐** `run / start / stop / status`；额外信息塞进 `status --verbose`，
   **不新增顶层动词**。保持「学会一个就会另一个」。
4. **改什么·改哪里**：本文件写死契约表；S3.1 按它实现。
5. **交付物**：动词 / 参数 / 退出码 / 输出格式的对照表（与 `bridge_cron.py` 并列）。
6. **验证**：逐条与 `feishu/bridge_cron.py` 的实现比对，语义不一致处必须有书面理由。

### S2.3 状态文件与配置落点
1. **解决什么问题**：pid / log / 状态现在散在 xhs 的 `_autopilot/`，搬家后要有确定去处。
2. **矛盾点**：Link16 的 `feishu/_state/` 已有大量桥状态文件，混进去会难以分辨归属；
   另立目录又增加认知负担。
3. **推荐方案**：**沿用 `feishu/_state/` + 统一前缀 `watchdog-`**（与 `bridge-session-` 同款命名法），
   不新建目录。日志进 `feishu/_logs/watchdog.log`，与 `bridge-cron.log` 并列。
4. **改什么·改哪里**：本文件写死路径表。
5. **交付物**：状态文件 / 日志 / 配置的路径表 + 是否进 git 的标注。
6. **验证**：所有路径都能用「仓库根起的相对路径」唯一定位；无一硬编码盘符或用户名。

## S3 · 通用能力落 Link16 — [ ]

### S3.1 新建 `feishu/bridge_watchdog.py`
1. **解决什么问题**：通用保活能力还没有 Link16 侧的家。
2. **矛盾点**：整文件复制会把 xhs 的 691 行债一起搬进来；从零重写又可能丢掉那三道
   来之不易的防自激闸（注入文本不含错误词 / 有 retry 就不碰 / 连续静止 2 轮 + 10 分钟冷却）。
3. **推荐方案**：**按 S2.1 的表逐函数搬**，只搬「通用 + 共用底座」；三道闸**原样保留、一行不改**
   （它们是踩过 livelock 才有的），并在代码里注明出处。
4. **改什么·改哪里**：新增 `feishu/bridge_watchdog.py`。
5. **交付物**：可 `python feishu/bridge_watchdog.py run` 跑起来的常驻部件。
6. **验证**：起来后能读到的面板数 ≥ 当前 workspace 数；日志逐轮有输出；`py_compile` 过。

### S3.2 修好断了两个月的名册接口
1. **解决什么问题**：告警标注「哪条 bot 线」自 2026-06-27 起一直是错的。
2. **矛盾点**：xhs 那 7 个僵尸文件还在原地，如果新代码仍能读到它们，会掩盖问题。
3. **推荐方案**：新代码**只读 Link16 的 `feishu/_state/`**，并用 `bridge_env.py` 的现成路径解析
   （不自己拼路径）；同时**主动检测**「读到的 pty 是否存在于当前 wmux 拓扑」，全不匹配就
   **明确报错而不是静默降级**——静默降级正是当初没被发现的根因。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `load_bot_names` 等价实现。
5. **交付物**：能正确标注 bot 名的告警。
6. **验证**：拿当前真实 pty 比对，标注命中率 = 100%；再故意喂一份陈旧名册，验证它**报错**而不是默默标错。

### S3.3 通知走 Link16 自己的发送链

### S9.1 voiceover 那套账本长什么样（实读 `runs/BENCH/BENCH-003/progress-ledger.json`）

一个 JSON，`schema_version: voiceover-progress-ledger-v1`，七个区：

| 区 | 是什么 | 为什么值钱 |
|---|---|---|
| `rows`（82 行） | 每个版本一行：`tag` / `at` / **三个分数** `lenient` `strict` `median` / `engine_ceiling` / `note`（这版改了什么） | **这就是那条 value function 轨迹**：v10 lenient 0.475 → v106 0.983 |
| `engine_ceiling` | 当前引擎**理论上能达到的最高分** | 把「我这次改错了」和「工具物理上做不到」**分开**。没有它就会对着一个够不着的分数一直撞 |
| `rejected`（6） | 指标**给了高分、但被人否决**的改动 | 反 Goodhart。原文：「指标奖励了一个更难看的画面」 |
| `tool_fixes`（1） | **尺子自己坏了**的记录 | 那条写着：记分板在缩到 320 宽之后算墨，离线工具在 1920 上算 → 同一屏 0.457 vs 0.647，**结论完全相反** |
| `fidelity_gaps`（6） | 东西是错的、**但分数看不见** | 原文：「这 6 个 checkpoint 已经 6/6、中位 0.968 —— 分数看不出这个差别」 |
| `lessons`（6） | 根因规则，每条带 **`why_it_hid`**（为什么当时没被发现） | 例：「并上多处改动时逐窗归因不是可选项——它是唯一能把『方向错』和『实现错』分开的东西」 |
| `blocked`（2） | 想做但被外部卡住，带 `why_it_should_work` + `blocker` | 卡住的事不会变成「悄悄放弃」 |
| `delivered`（4） | 哪一版被定为交付版、**凭什么** | 原文：「按【中位 + 逐窗】判，不按单一命中数」 |

**外加一个机制**：`checkpoint-attribution.json` —— **逐窗归因**。一次并上多个改动时，
它告诉你哪个窗口涨了、哪个跌了。没有它，一次 +8 一次 −8 会显示成「没变化」，
于是一个对的方向被误判成无效而放弃。

### S9.2 哪些能直接搬到「架构类任务」，哪些不能（主人让我探究的那个区别）

**根本差别只有一条：voiceover 的 oracle 是白送的，架构任务的 oracle 要自己造。**

原片就摆在那儿，逐帧可比、离线可重算、毫秒级出分。所以它的力气全花在**把测量做密**
（7 MB ground-truth、逐帧 checkpoint）。架构任务没有这个东西——没有一部「正确的看门狗」可以逐帧比。

| 维度 | voiceover（视觉还原） | 架构类（本 plan） | 结论 |
|---|---|---|---|
| oracle 从哪来 | **白送**（原片） | **要自己造**：旧看门狗的历史日志 / 重放语料 / 变异测试 | ❗最大差别 |
| 分数形态 | 连续、稠密（0.475→0.983） | 大多**二值**（起没起、通没通） | 需改造，见下 |
| 重算成本 | 渲染 28min，**打分几秒且离线** | 有些要重启桥 / 真起会话 = **贵且打扰人** | 需分层 |
| 主要失效 | 指标**奖励了错的东西**（Goodhart） | 指标**全绿但东西是坏的**（尺子坏了但输出正常） | 防御方向相反 |

**直接可搬（本 plan 已采纳）**：
1. `rows` 逐版一行 + `note` —— 值函数轨迹。
2. **多个分数而不是一个** —— 已有 `完成度`（二值）/ `质量度`（分档）两组。单一总分会让「功能全通但一身债」被掩盖。
3. **`engine_ceiling` → 每一维写明天花板** —— 这条在 S1.3 已经用血换过一次：
   C3 原判据「名册命中率必须 100%」**永远达不到**（名册里有 bot 当前没开会话），是个摆设门槛。
   改成相对判据后才有意义。**任何维度都要先问：满分理论上够得着吗？**
4. `rejected` / `tool_fixes` / `fidelity_gaps` / `lessons(带 why_it_hid)` / `blocked` / `delivered` 六个区——全搬。
5. **逐窗归因 → 逐维归因**：一次改多处时，必须能说出哪一维因为哪个改动而动。

**必须改造的两条**：
- **二值指标没有梯度，爬不上去。** ⇒ **凡能计数的都改成计数**。
  M2 不写「名册通不通」而写「命中活面板 **N** 个」；C7 不写「瘦身了吗」而写「行数 + 通用函数残留 **N** 个」。
  有了分子分母，卡住的时候才看得出「一直推不上去」。
- **重算成本不均。** ⇒ **分层**：
  · **L1 离线**（grep / AST / 读日志 / 纯函数重放）—— 每步都跑，秒级，零打扰；
  · **L2 半在线**（起进程、跑 `status`）—— 每个 stage 收尾跑；
  · **L3 真在线**（重启桥、真换一次号）—— 只在 stage 边界、且**先告知主人**。
  voiceover 不需要这层，因为它的 L1 就够；我们不分层就会因为「验收太贵」而干脆不验。

**架构任务独有、voiceover 不需要的一条**：
- **变异测试是刚需，不是加分项。** 视觉任务能用眼睛确认分数对不对；架构任务**看不见**，
  唯一能证明一道闸真的在守的办法就是**把它改坏、确认对应用例变红**。
  这就是 Q5 和 M6 存在的理由。**没变异测试的绿灯 = 没验过。**
