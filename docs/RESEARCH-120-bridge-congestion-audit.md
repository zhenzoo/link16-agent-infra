# 飞书桥为什么连关闭命令也会堵住

**这次主要是 Link16 把慢更新放在消息必经路径里，又让关闭命令排在它后面。网络请求可能触发慢等待，但把一次慢请求放大为整只 bot 无法控制，是桥的调度问题。** 故障时段没有 CPU、内存或磁盘空间耗尽的证据。

本次卡点已有现场和离线复现支持。更新、控制优先与重启恢复边界已修改，全仓最终回归1721项通过、3项跳过；生产桥仍运行旧进程，其他电脑本次现场尚未取得。

## 1. 这次消息实际停在哪里

以本机持久收件数据库的时间为准。飞书服务器时间与本机约有数秒差异，下面不拿两套时钟直接相减。

1. **23:19:08**，P304/P305 改稿消息已落到本机；**23:19:14**，补充链接也已落盘。飞书收消息这一步成功了。
2. 处理首条消息时，桥发现旧进程已退出，释放旧窗口绑定并准备重新启动。随后进入启动前更新。**23:23:54 桥被重启**，同一条未完成消息从持久队列续接；本次调查没有执行这次重启。
3. 新桥的更新检查从 **23:24:01** 开始，**214.306 秒后失败**，到 23:27:36 才进入 Codex 原生启动。更新器约 0.061 秒就有首次输出，但这不能证明之后仍有进展。
4. **23:24:16**，用户 `/close` 已落盘。它没有独立控制通道，直到 **23:28:06** 才轮到执行：在本机等待约 **230 秒**；23:28:10 关闭完成。
5. 前面的改稿消息在 **23:28:01** 获得原生 `turn/start` 接收回执，但几秒后排队的 `/close` 执行，刚启动的会话又被关掉。补充链接随后被关闭命令取消。于是会看到“终于启动，又关掉”的反直觉现象。
6. **23:28:20** 重发改稿后，又启动一次更新；23:30:07 的 `/close` 和 23:30:09 的 `/new` 都留在后面。23:38 现场仍能看到该 updater 及 PowerShell 安装子进程，连接本机代理 7897，尚未完成。
7. 后续只读复核：改稿直到 **23:46:34** 才完成交接，第二条 `/close` 在 **23:46:36** 完成，距收到约 **16分29秒**；`/new` 在23:46:51完成。本机后来已升级至0.167.1，00:08时旧updater已退出、队列继续工作。此自然恢复早于本轮代码修改，不是新修复已在生产生效。

“没有点赞”有另一层含义：Codex 普通消息的 👍 被设计为**原生智能体已接收完整正文**，并非“飞书桥已收件”。因此消息已经在本机排队，用户仍看不到 👍。这项接收证明应保留，但桥应该另行及时显示排队与卡点。

## 2. 为什么一行输出能卡住后面几分钟

本次故障时的调用关系为：

```text
飞书事件 → 每 bot 持久收件箱 → 单消费者逐条取消息
                                  ↓
                         等待会话创建锁与启动
                                  ↓
                         codex update
                                  ↓
                         PowerShell 官方安装脚本
                                  ↓
                         代理与外部下载请求

同一收件箱中的 /close、/new 只能等上面返回，再被取出。
```

`agent_update.py` 的五秒限制只管**第一段 stdout/stderr 是否到达**。一旦到达，程序直接 `process.wait()`，没有总时限，也没有“持续无进展”判定。桥调用它时还没传入进度回调，所以连“正在更新”的持续反馈也缺失。

官方 Windows 安装脚本本身关闭了 PowerShell 进度条；其中发布元数据请求允许 30 秒、资产请求允许 300 秒，部分 GitHub 回退请求未显式给超时。Link16 丢弃更新输出，只有结束后才保存成功/失败回执，因此现场无法从桥回执精确区分停在脚本下载、版本查询还是安装包下载。**有网络连接不等于下载有进展。**

原生启动的 60 秒就绪窗口在更新完成后才开始计时，不能限制前面的更新。已有 `/close`“已收到”提示也在消息出队之后才发送，因此并没有解决排队时无反馈。

## 3. 机器和网络分别能解释什么

**机器资源不支持“电脑扛不住了”这一解释。** 黑匣子在 23:18:29–23:29:59 的 24 个采样中：

- CPU：**12.2%–39.0%**。
- 内存：**45.6%–53.8%**；提交量为系统已承诺的内存，使用率 **41.9%–48.4%**。
- 温度：47.1–75.1°C；被动限频比例始终 100%，未记录该机制限频。
- 最少剩余空间：C 盘 28.3 GB、E 盘 230.4 GB。

这些是每 30 秒采样，不排除采样间的瞬时尖峰；但与“更新子进程长时间等待网络、关闭命令留在数据库队列”相比，硬件不是当前有证据的直接卡点。

**网络确有分路差异，但不能笼统说 VPN 坏了。** 23:38 的只读探测中，飞书入口直连约 356 毫秒成功；Codex 安装脚本经代理约 2.7 秒可读，直连超时；GitHub 发布页经代理约 2 秒可读，直连超时。它只证明当时这些入口的小段响应，不证明故障发生时的整包下载可用，更不证明模型请求正常。

23:27 还发生过约 17 秒飞书重连，但 `/close` 早在 23:24 已经落盘，重连无法解释其约 230 秒本机排队。

## 4. 为什么关机后又接回昨天的 Codex

**进程死亡和聊天历史保留是两件事。** Link16 在磁盘保存 bot 对应的 thread ID；原生 worker 新起时读取它，调用 `thread/resume`。本次启动回执明确为 `thread/resume`，恢复了 11 月 10 日的对话，所以至少这一条恢复是桥主动做的。

11 月 8 日的共享修改明确将“旧进程退出”改为只释放运行绑定、保留原对话。它原本用于中断恢复；现在用户已经改定：**仅关机或 Wmux 守护进程重启后，不恢复旧会话；同一次开机内意外退出仍可恢复。** 历史存档保留，供手动找回。

Wmux 4.10.0 确有另一层恢复：保存为 `exec` 的终端在恢复窗口时可以重放启动命令、接回精确会话。本仓桥创建普通工作区后向 shell 发送 launcher，没有把智能体注册为该 `exec` 启动单元；本次 `thread/resume` 回执也直接指向桥的原生 worker。**这次应先取消桥的恢复资格，无需关闭 Autonomy。** 后者管终端操作权限，不是恢复开关。本轮不修改 Wmux 安装文件，也不改变用户另外创建的独立终端策略。

修改使用桥已有的 daemon 指纹识别新实例；Windows 快速启动下系统开机时间可能不刷新，不能仅凭 boot time 判断。旧运行绑定释放时保留指纹，下一次启动仍能分清“同实例内崩溃”和“关机后重开”。只有指纹明确变化，才移除 Codex 自动 thread 指针、将 Kimi 自动指针标记关闭、解除 Claude 自动 transcript 绑定，并阻止旧任务自动注入“继续”；历史文件不删。指纹不变或未知时保留现有恢复资格。

## 5. 当前整改决定与证据边界

已经明确的更新语义：已确认最新版立即启动；确有升级与真实进展就继续并显示进度；检查失败、更新失败或连续数秒无进展时说明原因并使用现有版本，不能把“查不到”说成最新版。关闭应能取消正在等待的启动，取消后不得迟到创建会话。

已实施的最小修复：

1. Codex 先读官方发布元数据，检查最多等待 3 秒；已是当前发布版本不运行安装器，检查失败明确报告失败。发现更新仍调用官方 `codex update`。
2. 持续观察本次安装的下载文件增长、数值进度与安装阶段，连续 5 秒无进展结束本次尝试；真实进展持续时不设总时长上限。Windows 用专属进程 Job 收纳安装器及所有后代，取消时不会只杀父进程留下下载子进程。
3. 更新阶段通过同一张飞书卡片反馈；显示失败、最新版与升级完成三种不同结果，不再把“有输出”说成升级仍在正常进行。
4. 已授权且未过期的 `/close`、`/new`、`/stop` 优先于普通排队消息，彼此仍按接收顺序。正在更新、等 shell 或等原生启动的操作检查取消信号，释放启动锁后由正常控制路径收尾；未知身份、未获授权群命令和过期补发不能插队或取消。

离线同一假更新进程：先输出一行、再静默 1.2 秒。把无进展窗口缩为 0.3 秒，旧实现仍等 **1.260 秒**并成功返回；新实现约 **0.312 秒**返回 `stalled`。另以真实一次性子进程验证静默下载文件持续增长可以超过窗口继续，取消会结束其安装子进程。这里没有运行真实升级或发送生产消息。

## 6. 全链路审查：还会在哪里排队

**不是一根覆盖所有电脑的总管道。** 每个 bot 有自己的桥进程、入站队列和出站水位；同一 bot 的启动与注入仍需要串行，避免正文交错。共享 updater 按同一个可执行程序互斥，另一只 bot 检查到已有更新时直接跳过，不排队等待。因此本次“整只 bot 堵住”有明确局部来源，多台电脑可能同时带着同一缺陷，但不能据此宣布每台故障相同。

- **收件与原生提交之间：已确认的本次主因。** 消息已持久落盘，更新不结束就不进入原生提交。现有接收巡检主要覆盖已形成 handoff 的消息，启动前 `processing` 等待不在其告警范围内；此次进度反馈补上更新阶段，但不把它当所有准备阶段的完整监控。
- **定时任务：有跨 bot 等待风险。** cron 已先把所有到期任务登记入库，随后仍逐 bot 调用投递；一只 bot 启动慢，可以拖后同一 cron 进程中的其他 bot。登记保证待办不丢，但不保证准时。此次更新等待修复能消除一种长期阻塞，cron 各 bot 独立执行仍是后续调度改进，不在本次暗改并发结构。
- **出站：旧进度确实可能挡住后面的答案。** 新版进度卡发送与工作行闸在最终答案之前；失败时重试整批且不推进水位。离线输入“旧进度 + 已完成答案”，让旧进度工作行未就绪，结果为 `RetrySend`，答案发送函数一次也未调用。这是已复现的设计风险；本次现场 3.07 GB outbox 的水位正好到文件末尾，积压为零，故它不是此次启动拥堵的直接原因。下一步应把最终答案的可靠送达与可重试进度显示解耦，保留原有逐片 ACK、防重放与路由合同后再改。
- **大文件：运行与诊断要分清。** 出站 drainer 从已确认水位增量读取，不是每轮重扫 3.07 GB；不过它一次读取全部未读尾部，离线很久后的大积压可能挤占事件循环。`bridge_history --recent N` 则确实先全量读取再取最近 N 条，本次调查也遭遇等待。应分别用大积压样本验证分批语义、为历史查询做尾读或索引；不能粗加 2 MB 上限破坏既有进度计数。
- **已修过的故障没有覆盖此次缺口。** PLAN-1110 解决原生启动就绪判据；PLAN-1120 解决收件持久化与桥重启恢复；PLAN-1220 解决数据库 WAL/锁竞争。这三项分别管“是否就绪”“消息是否丢失”“数据库是否拿到锁”，都不能约束拿到锁之后无限等待官方更新。

整改顺序是先让本次已证更新故障可退出、控制可取消，再按真实故障样本处理 cron 隔离与答案通道；不以更换电脑、加内存或盲改 VPN 代替这两个软件边界。

## 7. 验证与生效范围

**代码与隔离验证已完成，生产重载待维护窗口。** 最终全仓1721项通过、3项跳过、203子测试通过；另用本机真实官方接口验证版本检查约1.37秒返回0.167.1，完整 `ensure --profile cxp` 约1.48秒确认本机已最新，未运行安装器。测试覆盖无输出、仅开场、重复提示、持续文件增长、真实子进程解包写入、数值进度、快速失败、取消及整棵安装子树退出；控制侧覆盖顺序、未授权/过期不抢占、shell/原生等待取消、单卡更新和不明创建不重发。

三runtime的共用启动路径、恢复指针和同/异/未知daemon边界均有fixture回归；真实安装进程树在Windows验证，POSIX进程组路径未在本机执行。本轮没有执行整机关机、Wmux daemon重启、真实飞书控制命令往返或其他电脑验证，也未运行新版本代码的真实升级分支；不能把当前最新版检查当整条启动上线验收。

建议维护动作只执行 `python feishu/feishu_bridge.py start --bot tb24-xhs-autopilot`，按现有生命周期控制替换这一只桥，保持Wmux、已有原生会话和其他bot不动；核新PID/ready、收件状态、原生进程与绑定保持后，再观察真实消息。用户确认维护窗口前不执行。其他bot与cron仍需各自自然重启或后续明确维护范围才能加载常驻部分。
