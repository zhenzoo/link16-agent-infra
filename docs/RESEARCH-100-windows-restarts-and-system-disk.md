# 凌晨更新重启与 C 盘持续增长：调查结论和处理方案

**结论：凌晨中断由 Windows 更新主动重启引起；C 盘空间不足是另外一个已确认的问题。长期处理应同时关闭 Windows 自动更新，并把持续增长的数据迁出系统盘、给可再生缓存设置保留上限。**本轮按主人要求只调查和提交方案，没有更改更新策略、停止服务、重启电脑、删除数据或迁移账号。

## 一、以后不自动更新、不因更新自行重启

### 为什么这次在凌晨发生

本机系统是 Windows 11 专业版。9 月 15 日 04:14 开始安装安全更新 KB5129195；04:44:18，Windows 更新进程 `MoUsoCoreWorker.exe` 发起第一次计划内重启；04:46:12，系统安装程序 `TrustedInstaller.exe` 再次发起计划内升级重启；04:47:29 记录安装成功。

两次都有明确的发起程序和正常关闭记录。在昨夜查询窗口内，没有查到意外关机事件 41/6008，也没有对应的磁盘错误事件。因此，证据支持“更新触发了这次重启”，不支持“C 盘满导致这次断电或蓝屏”。9 月 10 日 03:29 和 03:34 也发生过同类更新重启。

当前使用时间设为 09:00 至次日 03:00，凌晨 4 点在这个时段之外。Windows 会在使用时间之外安排更新重启；使用时间最多覆盖 18 小时，不能满足全天运行的要求。[微软更新重启说明](https://learn.microsoft.com/en-us/windows/deployment/update/waas-restart)

### 建议采用的长期设置

以“Windows 不再自行下载、安装更新，重启由主人决定”为目标，在本机专业版上使用系统支持的策略：

1. **将“配置自动更新”设为“已禁用”。**对应机器策略为 `WindowsUpdate\AU\NoAutoUpdate=1`，没有暂停若干天后自动到期的时间限制。微软明确说明，禁用后，可用更新必须手动下载和安装。[微软自动更新策略说明](https://learn.microsoft.com/en-us/windows/deployment/update/waas-wu-settings)
2. **同时关闭设置页的 Windows Update 操作入口，减少误点触发。**对应机器策略为 `WindowsUpdate\SetDisableUXWUAccess=1`。这项单独使用只限制入口，必须与第一项配合，不能把“按钮消失”当成后台更新已经停止。[微软更新访问控制说明](https://learn.microsoft.com/en-us/windows/deployment/update/waas-wu-settings)
3. **将“Windows 更新不包括驱动程序”设为启用。**对应 `WindowsUpdate\ExcludeWUDriversInQualityUpdate=1`，为以后其他设置改变时的驱动更新增加一层明确约束。这只管 Windows Update 通道，厂商独立更新器要分别盘点。[微软驱动更新策略说明](https://learn.microsoft.com/en-us/windows/deployment/update/waas-wu-settings)
4. **保存更改前的精确配置，并检查配置是否被改回。**后续可接入已有 Link16 巡检报告策略漂移，避免再增加一个独立看门狗。巡检只报告，不能悄悄重启机器或扩大到其他软件。

正式执行时，先导出本轮涉及的策略值，检查有无正在安装或已提交的重启，再应用上述设置并回读有效策略。07:59 查询的三个常见待重启标记均不存在，但这只是本次采样结果，执行前仍应重新核对。

**验收不能只看服务有没有运行。**应同时确认有效策略、更新入口状态，以及后续观察窗口内是否出现新的自动下载安装和更新发起的重启事件。无需为测试主动重启电脑。禁用自动更新的目标可以长期保持，但系统重装、修复、管理员或管理软件覆盖策略后仍需重新验收；也无法阻止断电和硬件故障。

停止 Windows 系统更新也意味着不再自动获得相应安全修补。此方案针对 Windows 系统自动更新；杀毒病毒库、浏览器和应用自身更新是独立通道，不能宣称上述三个设置已把所有软件更新一并关闭。

## 二、让 C 盘不再依赖反复手工清理

### 实际是谁在占空间、谁正在增长

C 盘总容量约 248.7 GiB，07:41 可用 8.2 GiB，07:59 降至 7.5 GiB。下表是本次文件体积统计，GB 展示沿用 Windows 常见的 1024 进制口径，精确单位为 GiB。

| 对象 | 本次体积 | 对问题的意义 |
|---|---:|---|
| Codex 个人账号完整会话目录 | 13.34 GiB | 长期归档会持续积累；不能当作可随意删除的缓存 |
| 两个 Claude 个人账号项目记录 | 4.99 GiB | 与另一个 Codex 账号约 0.23 GiB 合计，聊天记录约 18.6 GiB |
| npm/npx 下载及运行缓存 | 9.45 GiB | 其中 npx 约 8.32 GiB，存在多版本工具及依赖副本 |
| 用户临时目录 | 5.25 → 5.86 GiB | 两次采样间增加约 625 MiB，是本次查到的快速增长位置 |
| pip 下载缓存 | 1.19 GiB | 可以改写入位置，并对可再生内容设置保留规则 |
| 通用用户缓存目录 | 5.16 GiB | 混有模型、浏览器和正在使用的运行时，应分组件处理 |
| Miniconda 安装、环境和包目录 | 13.84 GiB | 较大的基础占用，旧环境不能直接拖走后假定还能用 |
| Chrome 用户数据 | 7.85 GiB | 含约 3.98 GiB 的本地模型，不全是普通网页缓存 |
| 系统休眠文件 | 11.08 GiB | 属于系统功能占用，不是本次聊天增长 |

**这次增长有两次采样作证。**临时目录增加约 625 MiB，其中 `Temp\claude` 增加约 614 MiB；同期 Codex 个人会话目录仅增加约 1.5 MiB。`Temp\claude\bash-edit-diff` 当前约 2.66 GiB，包含多份约 200 MiB 的 Git 文件差异临时库，早晨新建了多份。抽样比较三个目录的同名大对象，文件标识各不相同、硬链接数均为 1，确为独立文件副本。

目录名含 `claude` 不足以证明创建者就是某一版本的 Claude Code。目前已定位文件增长位置和快照形态，创建进程、触发条件及清理责任仍需在实施时进一步关联。不能把这个尚未查明的部分写成“已修复的 Claude bug”。

**聊天 JSON 也确实会很大，但不是只有对话文字。**抽查一个 477.5 MiB 的 Codex 会话：普通消息记录约 0.45 MiB；工具返回记录约 322 MiB，上下文整理快照约 81 MiB，其中大量记录包含图片数据。含图片的记录行合计约占文件 81%，此比例包括这些行的其他内容，不等于纯图片字节比例。顶层 `history.jsonl` 本身只有约 1.8 MiB，删它释放不了多少空间，真正的大头是完整会话目录。

开发工具也会重新下载依赖：npx 缓存有 27 个目录，抽样发现多个 HyperFrames 版本各占约 360 MiB，其中一个目录在今日 01:10 创建。旧缓存删除后，仍沿默认路径运行工具就会再次写回系统盘。

没有上次清理前后的历史容量快照，不能给出“昨夜总共新增多少”的精确值，也不能用文件修改时间对应的当前总大小冒充新增量。当前 Windows 更新下载目录仅约 0.27 GiB，关掉系统更新不会自动解决上述应用数据的增长。

### 建议实施顺序与改后效果

**第一步，先改变以后写到哪里，再迁移旧数据。**

- 将开发工具的 npm/npx、pip 缓存和任务临时目录统一指向数据盘；`TEMP/TMP` 和工具自己的缓存配置需一并检查。优先使用软件支持的配置项，npm 的 `cache` 配置及其环境变量机制已有官方说明。[npm 配置文档](https://docs.npmjs.com/cli/v11/using-npm/config)、[pip 缓存说明](https://pip.pypa.io/en/stable/topics/caching/)
- 将各账号的完整聊天记录目录迁至数据盘。没有独立路径设置的目录，可在确认兼容后使用目录联接：程序仍访问原来的目录名，文件实际写入数据盘。先验证历史恢复和新增消息落盘，不能只验证目录存在。
- 迁移期间暂停对应目录的写入，先复制、核对文件和抽样哈希，再切换入口并验证。通过后才能释放旧盘副本；“只复制”不会释放 C 盘。账号身份仍以 effective registry 为准，不能因此混合账号配置或认证。
- 进程已启动时不会自动继承后来修改的环境变量。需要在约定窗口重新启动受影响的应用和会话；涉及生产桥时仍遵守维护窗口要求，无需重启 Windows。

聊天记录、npm/npx 和 pip 三项合计约 29.2 GiB。若能完整迁出并释放旧副本，按本次容量约可让 C 盘从 7.5 GiB 可用恢复至约 36.7 GiB。再处理已确认不用的临时快照、其他可再生缓存，**建议验收目标为 C 盘至少保留 40 GiB 可用空间**；实际释放量以磁盘回读为准，不把逻辑目录体积当成保证值。

**第二步，约束产生和保留，避免数据盘也再次爆满。**

- 对文件差异临时库：定位创建者和完成信号，任务结束后回收；异常中断遗留进入定期回收。必须确认相关任务已结束，不能仅凭目录年龄或一个 `index.lock` 就删除。
- 对 npm/npx：常用工具固定受管理的版本和运行位置，减少每次按新版本生成整套依赖副本；已不再引用的旧版本缓存按容量和使用情况回收。
- 对诊断日志：使用组件支持的日志轮转或保留策略，达到设定体积后轮换；正在使用的 SQLite 数据库不能直接截断或删除。
- 对聊天记录：默认保留，按月归档并保留检索索引；压缩或冷归档前确认历史恢复方式，不能为了省空间破坏继续会话的能力。它和可再生缓存采用不同保留规则。
- 对磁盘：记录各大目录体积及增量，建议 C 盘低于 40 GiB 提醒、低于 20 GiB 阻止受管任务继续创建大量临时数据。数据盘同样设置余量和归档触发值。这里是实施建议，当前尚未安装这些规则。

**第三步，仅在以上仍不够时调整容量。**

本机 E 盘尚余约 170 GiB，第一批迁移可利用这部分容量；它也已有大量数据，不能被视为无限存储。C 和 D 在同一块约 512 GB 物理盘，C 与 D 之间隔着恢复分区；E 在另一块物理盘。不能直接把 E 盘容量加给 C 盘。分区调整或更换系统盘可以增加余量，但不会解决无上限的缓存和归档写入，因此不作为首选。

这个方案的长期结果应是：**系统盘保持余量，聊天历史继续可用，可再生临时数据自动受控，主人不用反复手工清理。**若要求无限保存所有内容，任何有限硬盘最终都需要外部归档或扩容，不能承诺完全没有容量管理。

## 补充：磁盘空间和运行内存是两个问题

昨晚 18:22、18:27 还出现过虚拟内存不足事件，涉及浏览器和 Claude 进程。这能解释部分程序卡顿或退出，但不是凌晨更新重启的证据。当前分页文件已在 D 盘，约 27 GiB；腾出 C 盘不会直接增加物理内存。若继续出现程序内存不足，应另查浏览器实例和任务并发，不能把两个问题混为一谈。
