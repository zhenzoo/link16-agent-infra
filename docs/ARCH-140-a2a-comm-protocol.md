# ARCH-140 · Agent↔Agent 通讯协议（a2a comm）—— 请求自动回 peer，结果不反射

> **类型**：ARCH（讲它怎么运转）· band 1xx = feishu 桥
> **职责**：定义**智能体之间**怎么经飞书桥对话。
> **与 [`ARCH-110`](ARCH-110-feishu-bridge.md) 分工**：ARCH-110 = 桥本体（@bot→注入 / hook→outbox→drainer 回传 / 多 bot）；**本档 = 架其上的「agent 之间怎么对话」那层**。
>
> **2026-10-07 当前合同（主人已授权，部署/真机验收见 PLAN-1140）**：同群与跨租户 peer 来信都保留 `a2a` 身份。请求的最终结果由桥自动回请求方，不默认 DM 主人；结果引用原 `mid`，仍注入发起方会话，但不自动反射回复。复用现有发送工具、戳、镜像和账本，不新建通讯系统。

---

## §1 · 一句话模型（就这一条）

> **谁提出请求，最终结果回给谁；收到 peer 结果可以继续工作，但不自动回“收到/谢谢”或转发主人 DM。tenant 仅决定发送通道。**

跑一遍（A 喊 B 干活）：
- **A 喊 B**：A 主动 `send_feishu_msg --to-agent B`（自盖 `[飞书_from_A_to_B]` 戳）→ 进共享群、@B。
- **B 收到请求** → 桥保存 `route=a2a peer=A mid=<本条请求ID>` → B 正常输出最终答案 → 桥复用发送工具自动回 A，并盖 `[飞书_from_B_to_A reply_to=<原请求ID>]`。无需 B 记住另调发送工具。
- **A 收到 B 的回信**（桥注入 A 会话 · A 读到了）→ A 判断：
  - **没别的要谈** → A 读到结果；桥对本轮普通输出记“结果已消费、抑制外发”，不发群、不发主人 DM。不是丢弃入站回信。
  - **要续第二轮**（发现问题要讨论）→ A **再主动 `send_feishu_msg --to-agent B`（带戳）** → 又一轮进群。

**对照**：主人私聊仍回 DM；真人群请求仍回原群；peer 请求回 peer，peer 结果不自动续轮。主动通知/新问题仍显式 `send_feishu_msg`。

## §2 · 为什么是这个模型（演进 · 别再走回头路）

- **v0.3 旧**：桥收对端回信（尾缀哨兵 `PEER_LOOP_MARK`）→ **扔掉**防环；发起方靠 `--wait` 守望才收得到。**洞**：不守望就收不到。
- **v0.4（07-02 简化）**：删守望+哨兵，桥**无条件路由**每轮输出回群、当普通消息。**洞（07-03 实证）**：**死循环**——A 输出→群→B、B 输出→群→A…无限（tb24-notes-2 ↔ tb25-tennis-post 空转 160 条）。且 agent「想停」也停不掉：**这一轮 route 焊死 a2a → 它 terminal 输出任何字都被桥推回群**（主人实证：agent 说「我不发了」照样被推群）。
- **v0.5（07-03 熔断 · 已废）**：加「连续 N 条低内容/短消息 → 熔断+静音」兜底。**问题**：靠 N 数轮数兜底、不简洁、烧 token；**客气环**（🤝对齐/🫡待命·有内容不重复不好抓）；且根本矛盾没解——只要 route 固定 a2a，agent 输出就必被推群。
- **v0.6（07-03 本档 · 真解）**：**改路由**——agent 普通输出**默认回主人**、发 peer **只能主动带戳 send**。**循环结构上没了**（见 §2.5）。熔断/结束工具/短触发**全删**。
- **v0.7（10-07 当前）**：v0.6 的“必须记得主动回 peer”允许 LM 漏发而正常结束，主人 DM 又逐轮收到噪声。改为桥自动回请求方；在原身份戳补 `reply_to=<已有 mid>`，接收结果仍注入，但抑制其自动外发。身份戳不等于回信关系，旧隐形哨兵直接丢弃回信的做法不恢复。

## §2.5 · 当前模型为何不形成自动循环

- **一条请求只产生一份自动结果**：最终答案通过既有 outbox 分片/ACK 回 peer，引用请求的已有 `mid`。长文可有多个有序片段，每片都是同一请求的结果，不是新请求。
- **结果不自动反射**：入站戳带 `reply_to` → 结果仍注入会话；该轮 progress/answer/ask 的自动外发被抑制，记录消费回执，不伪造发送成功或 message_id。
- **完成回址不复用**：首个 final 钉住后，现有 active=false 封口该 peer 回合；Stop 检查续跑没有新来信就不再产出网络结果。A2A progress 也不得编辑原主人卡；同一 runtime turn 被 steering 复用不改变规则。首次真机曾发现这两个遗漏，修复与重测证据见 PLAN-1140，不能把初测算通过。
- **续轮仍靠明确动作**：读完结果发现新问题时，显式 `send_feishu_msg --to-agent` 发一条新请求。人为/LM 刻意重复派活不属于自动反射循环的保证范围。
- **不恢复旧设施**：不加计数熔断、守望、静音或第二队列。跨租户本方镜像仍不 @，不会唤醒 bot。
- **失败不偷换对象**：peer 发送失败保留未 ACK 片，不回退主人 DM；已确认目标送达后的镜像或账本失败不能诱导重发目标。

## §3 · 结构化信号（判定只认这些）

| 信号 | 含义 |
|---|---|
| `[飞书_from_<发>_to_<收>]` 戳 | 沿用发收件身份；主动新请求不带回信关系。自动结果或显式 `--reply-to` 在同一戳内补 `reply_to=<原请求 mid>`，不另造 ID。 |
| 信封 `route=<p2a\|p2a-ext\|a2a>` | `p2a` 只用于真人 DM/终端默认；`p2a-ext dest=<群> at=<真人>` 回原群；peer 为 `a2a peer=<发件名> mid=<本条ID> dest=<入站群> at=<SDK发件ID>`，可附 `reply_to=<原请求ID>`。逻辑回信对象只认 peer 名册，不能把 webhook 的 SDK 发件机器人当 peer。精确字段与出站 ACK 见 SPEC-210。 |
| `msg_type == "text"` | a2a 必走纯文字（飞书把卡片渲成占位 `[interactive]`，对端读不到正文）。 |

呈现矩阵由 route kind 唯一决定：`p2a` 私聊 final 是互动卡片，`p2a-ext` 真人群 final 是 1～N 张互动卡片并 @发起人；a2a 新请求与自动结果是纯文字并 @peer，关联结果的接收回合没有自动外发。`oc_` 只说明 receive ID 类型，不能用来判断消息格式。

## §4 · 工具原语（全在 `feishu/`）

| 原语 | 谁用 | 职责 | 工具 |
|---|---|---|---|
| **send（共用 peer 发送实现）** | agent / 桥 | 新请求/主动通知走 CLI；请求最终结果由桥复用 `send_agent_message`。两者都解析名册、盖戳、@peer，并按租户选择应用发送或 webhook | `send_feishu_msg.py --to-agent B --text "…"`；显式回信加 `--reply-to <mid>` |
| **read（兜底手动读群）** | 任何人 | 一步读群 recent | `bridge_feishu_probe.py --bot A --group --recent N` |

> **a2a 行为规范（agent 必读）**：
> 1. 收到 peer 请求，正常最终答案会自动回它；不要再手动补投同一结果。
> 2. 收到带 reply_to 的结果，读完自然停止；不要发收到/谢谢，也不逐轮 DM 主人。具体新问题才显式 send。
> 3. 主人明确要汇报、需要拍板或故障需介入时才另外通知；不能用主人可见代替 peer 送达。

## §5 · 不变量 / 红线

1. **同群与 webhook 共用一种 A2A 身份和发送实现**；peer 请求最终答案回 peer，结果轮不自动外发，不默认 DM 主人。
2. **循环靠明确请求/回信关系及结果轮抑制外发切断**；不靠数轮数、判长度或 LM 记得调用工具。
3. **a2a 必走纯文字**（卡片对端读不到）。
4. 读/发都走共享群（`shared_group` 现解析 · 禁硬编码 `oc_`/`ou_`）。
5. active turn 若正要自动回同一目标，`send_feishu_msg.py` 在联网前拒绝手动补投；确实是额外通知才显式 `--proactive`。不同 peer/不同群不受影响。

## §7 · 外部通道（对外群 · 外部真人）—— 定义在这里，任何 session 读它就懂

> **场景**：某 bot 进了**群**（对外群如 `tb25-jiuzhouMV` 在「对外群A」，或内部编排群），群里**真人**（外部人如黄滟，**或 owner 本人**）@ 它 → agent 回复回【该群】+ @他（2026-07-05 主人拍板：只要是群、不区分内外，owner 也回群不回 DM）。这套怎么走、名字哪来、用哪些工具——**全定义在本节 + 代码，不靠某个 agent 记着**（session 关了、换人、换群，下个 session 读这节就全懂）。

### §7.1 · 铁律：一切名字【有源头·API 查·绝不硬编码/凭记忆】
群名、人名**都不准硬编码、不准凭记忆猜**——必须是**飞书 API 现查**到的（就像 bot 的 open_id/显示名一样有源头）。落成文件（名册/缓存）只是 API 结果的落盘，源头永远是 API。反例教训（2026-07-05）：把 `ou_f8dd…` 凭「听来的」当成「朱健」，API 一查其实是「朱镇」——所以名字只信 API。

### §7.2 · 三件事怎么运转
| 环节 | 怎么走 | 源头（API）| 落哪 |
|---|---|---|---|
| **回信路由** | 群里【任何真人·含 owner 本人】（群 + 无 a2a 戳 = 不是 peer bot）→ 信封 `route=p2a-ext dest=<群> at=<发信人>` → 回**原群 + @他**（见 §3·2026-07-05 主人拍板：owner 群内 @ 也回群、不回 DM·撤掉旧「≠owner」排除） | —（结构判定）| 代码 `feishu_bridge.py` on_message + `_route_to_dest` |
| **`via=<群名>`** | chat_id → 群名 | `im/v1/chats`（群列表·`send_feishu_msg._bot_groups`）| **`agent-registry.json` 的 `groups` 段**（committed SSOT·`registry.py sync-groups` 拉）|
| **`from=<人名>`** | 发信人 open_id → 人名 | **`im/v1/chats/{chat_id}/members`（群成员·用 bot 自己 `im:chat` 权限读群·不碰 owner 账号）** | **本地缓存** `feishu/_state/people-cache.local.json`（gitignore·桥遇新外部人自动查+缓存）|
| **@ 那个人** | 回信里 `<at id=<open_id>>` | 飞书**自动把 open_id 渲染成他的名字** + 通知他 | —（不落盘·飞书现渲·所以 @ 永不硬编码名字）|

### §7.3 · 工具 / 路径（要用哪个查哪个）
- `python feishu/registry.py sync-groups` —— 把某 bot 所在群拉进名册 `groups` 段（群名的源头）。
- `python feishu/registry.py group-name <chat_id>` / `resolve-person <open_id>` —— 查群名 / 人名。
- 群成员现查 = `im/v1/chats/{chat_id}/members`（桥内 `_resolve_person` 自动调 + 缓存）。
- 发东西到对外群 = `send_feishu_file.py`（视频/文件）/ `send_feishu_msg.py`（文字 + `--at` @人）。

### §7.4 · 安全（主人决策 2026-07-05）
对外群**不加「外部人只读」限制**——外部真人**既能收回复、也能派活给 bot**（此 bot 专为对外群操作·群放行不变）。将来某群若要限制，可做成 per-群 knob。peer 请求/结果按 §2.5 防自动反射，真人群回址不受影响。

## §8 · 跨租户 a2a（企业租户 ↔ 个人租户 · 2026-09-26）

**问题**：飞书应用属于注册时选的租户。企业自建应用的 bot 不能给另一个租户的群或 bot 发消息——「对外共享」要企业管理员审批，权限审计里也没有能绕开它的免审 scope。TB26 的 OBSBOT 企业 bot 与 TB24/TB25/TUF19 的个人租户 bot 因此互相喊不到（09-08 实证三次被拒）。

**做法**：每个租户的共享 a2a 群里各加一个**自定义机器人**（群机器人 → 自定义机器人，免管理员审核）。webhook 是这个群的「投信口」：任何网络向它 POST 纯文字就会出现在群里，文字里的 `<at user_id="ou_…">` 会像 peer bot 的 @ 一样唤醒群里的应用机器人（需要收件 bot 已有 `im:message.group_at_msg.include_bot:readonly`，舰队基线已含）。桥照常注入，发件人仍按 `[飞书_from_X_to_Y]` 戳认出。一个投信口只进一个群，所以双向需要两个：企业群的管「个人 → 企业」，个人群的管「企业 → 个人」。

**路由**（`send_feishu_msg --to-agent`）：名册里发件 bot 与收件 bot 都登记了 `tenant_key` 且不同 → 取收件方租户的 `webhook_env`，从本机 `.env` 读地址后经 webhook 原样投递（文字 + 真 @ 标签 + 发件人戳，不另加前缀），路由记为 `a2a-webhook`；任一边没登记 `tenant_key` 或相同 → 原来的共享群路径不变。投递成功后，发件 bot 再用自己的应用把同一段话**原样抄一份到本方租户的群**（不 @ 任何人 → 不唤醒、不成环），两个群因此都能看到完整往来，主人任一账号都看得懂（09-26 主人要求）；抄送失败只提示，不影响投递。收件租户没登记 webhook、或本机 `.env` 缺地址 → 当场报错，不退回别的群。

**实测**（tb26）：09-26 23:27 企业群投信口 @ tb26-link16，4 秒注入会话；23:55 `send_feishu_msg --bot tb26-link16 --to-agent tb25-link16` 自动走个人群投信口，飞书返回成功并写入出站账本。

**边界**：`tenant_key` 只按实测填（`tenant_probe.py` 或 im/v1/chats），判不出就不填。两个自定义机器人都不开签名/关键词/IP 限制（主人 09-26 定），webhook 地址因此等同口令，只放各机 `.env`。@ 必须是 `<at user_id>` 标签：手写「@tb26-link16」只是文字，不会唤醒（09-26 23:46 tb24-link16 手写回信实证）。企业 → 个人群发出的只限同步通知，不发公司资料。
