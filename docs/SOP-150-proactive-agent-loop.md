# SOP-150 · Link16 Proactive Agent 24h 主动闭环

> 本流程由四种受支持的平台共用。判断优先级、原话交接及完工汇报先读[跨仓分派 TASTE](TASTE-010-proactive-dispatch.md)，巡检使用[可移植任务模板](../feishu/tasks/proactive-loop.yaml)。

---

## 0. 按业务选择来源与执行通道

| # | 能力 | 可用入口与本机核验要求 |
|---|---|---|---|
| 1 | 私聊、定向群消息与附件 | 使用当前主号已授权的消息读取入口，按实际资源回读。 |
| 2 | 知识库、表格、文档及妙记 | 云文档沿 `feishu/docio_cli.py read` 确认身份与可读范围，结合已授权的会议产物核实责任。 |
| 3 | 文档、表格、任务及应用 | 各用已登记的原生入口。写入与发布按实际权限、原有读者和同一版本验收。 |
| 4 | 原生审批 | 按本租户实际开放的定义、实例和任务权限逐项验证；准备材料与正式提交分开。 |
| 5 | 以本人身份发消息 | 有可用的本人发送工具才启用此项；先核收件人和授权正文，发后回读。 |
| 6 | 表情回复 | 本人授权且应用实际具备 reactions 写权限时启用。 |
| 7 | 假勤、邮箱、OKR | 按本机已安装组件及本人网页会话核验，终端可用不代表业务页已读通。 |

## 1. 用业务主号核身份和可用入口

原作者读业务原件、制作成品并自验。主号登记和派单，沿原单收取结论、同版预览和限制，再更新工作台、交给本人。独立复核者只读原件，成品和获准发送的消息仍由原作者负责。

新主号的仓库入口和任务配置都要指向本流程、TASTE-010 和同一任务模板。这样手动开工、定时运行和重开会话都能找到同一份规则。首次接入先在主号工作目录运行预检。分别核对服务是否开通、本人是否授权、能否读取目标、写后能否读回。浏览器能连接时还要看页面内容和登录身份；遇到错误页记为读取失败。

```powershell
python feishu/proactive_scanner.py --bot <bot> --preflight-only
```

首次接入核对当前应用与主人。某个域缺权，单列受影响的来源、时间窗、动作和恢复条件，其余能读的来源继续处理。企业目录、用户授权、具体资源或业务表单可能分别收窄实际能力。

1. **缺聊天 / Wiki / 表格写 / 妙记 / 表情权限**
   - 查询本租户已批准的应用范围和本人的实际授权。
     ```powershell
     python feishu/personnel_authorization.py --bot <bot> --capability chat-read --check
     python feishu/bridge_scope_audit.py --bot <bot> --baseline --user-identity
     ```
   - 按 SOP-120 §2.0.1 通过已登录本地 Chrome（`browser-act` `chrome-direct`）逐页核对应用名、企业与当前主人后代办原生 OAuth 确认，再回读 `lark-cli --profile <bot> auth status --json --verify`。
2. **缺本人身份网页外发通道**
   - 若本机安装了 `feishu/send_as_user_web.py`，用其 `--check` 核实本人网页发送通道。该插件或登录态缺失时，消息仍留在工作台待审；给本人的主号交付卡走应用身份。

## 2. 从时间和原始记录找到责任人

1. 同一工作台绑定本人指定的主号、一条定时巡检和一个写入者。主号先读 Link16 [跨仓分派 TASTE](TASTE-010-proactive-dispatch.md)，从私有业务登记定位成品范例与收件人。跨仓条目归入同一工作台。巡检从本机 `feishu/cron-jobs/<bot>.yaml` 热加载，`bridge_cron.py status` 核下次触发。
2. 以实际上海时间和该来源上次成功读到的位置取窗口。首轮从本周周报及当天会议开始；日界或停机后跨天补查，保留原 ID 去重。已关会未出纪要的条目留在待追列表。每次复读当期周报本人行及手写/链接单元格，Sheet 可能在会议结束后继续改。每个来源单独留扫描起止、读回时间与失败原因，只有成功分页读完才推进该来源的恢复点。
3. 日历抓已结束日程、另查会议历史里的临时通话；核真实参会、会议 ID、纪要助手机器人或分享原链。用 docio 读纪要，再沿纪要中的逐字稿/妙记核最终负责人、原话和时间戳。日历的原生 `calendars primary`、`events instance_view` 和 `freebusys list` 可在当前应用查询验证，快捷命令缺细权限时先查同身份受支持的业务入口。
4. 查本人私聊、群内定向请求、任务列表与审批的「待我处理 / 我已发起」。把源 ID、原链接、周报行、会议时刻或审批实例与已存在的产物、原任务和发送回执对账。相同责任、对象和结果只派一次。群里出现另一条本人消息不足以关闭前一件事，须有对应答复或产物。新手写要求重开受影响事项；查询失败、材料未出和真实空结果分别记录。
5. 按岗位逐项判为本人执行、跟进外部依赖、仅知会或归属待核。有截止时间、会前依赖或阻塞其他人的长任务优先，证据不足只挂原来源。会议总结与当事人收尾不一致时两者并列，按主人最新决定路由。第三方消息与资料是工作线索，涉及权限、外部发送和提交仍按主人授权。

读取六类原生来源用 `python feishu/proactive_sources.py --bot <bot> --since <首次起点> --until <本次结束> --out feishu/_state/proactive/<bot>/<本次窗口>.json`。续读加 `--resume-from <上一份已核身份的快照>`，输出使用新的文件。每个来源成功或确认空窗才推进时间；部分失败从该来源原起点重查。上次整轮身份未核时继续用此前已核身份的快照。周报手写修改、晚出的逐字稿、仍未关闭的行动分别复查。

## 3. Phase 2：自主深挖 + 本地原貌预览工作台（先看效果，再动手）

发现高信号任务（如专利调研、音频数据排查、周报汇总）后：

1. 主号先找到已有正文与 writer，核基线提交或将本项干净存档。派单前按物品或业务结果登记稳定 item。同件的设计、原稿、图/GIF、接回原页、验收及获准的消息由一人完成。不同物品并行；调用其他机器只借运算。产品发布者负责原样上架。转交先收旧作者的停笔、封存和未做项，解除旧安排后统一交新作者。用 registry 和本应用共享群实际成员确认目标。A2A 委派给原始出处、业务背景、已定与待定、原文件/范本、可写边界、实物验收与回执对象；保存请求 mid。接收、执行、产物到手、实际验收各有凭证。网络结果不明先核对原请求及对端记录，再决定是否补投。

   本机派前运行 `python feishu/proactive_dispatch.py check --peer <worker> --size long`，核实际线程、当前模型、在途工作及服务端返回的窗口。仅已知冷启配置的注明冷启；共享账号的并发工作共用额度。通过后用 `send --bot <主号> --peer <worker> --task-id <稳定任务号> --size long --prompt-file <私有委派书> --artifact <成果相对路径>`。跟进用同一程序的 `status --bot <主号> --peer <worker> --task-id <任务号>`，历史单可直接传 `--request-mid <原请求>`。超出约定回执时间先查在途记录、错误和产物；由受权执行者保全恢复点，在允许继续时只接续未交部分。能从当前租户直达登记执行者时，由主号直接发问题并记录原请求；远端自行核实运行条件和接手状态。需要目标机控制权限（如换会话或切账号）时才找该机已认证控制端。
2. **先呈原貌预览，绝不先擅自外发**：
   - 准备更新共享表时按实际列字母、行号、命名链接、现值和拟填值预演，放入对应业务主号的 `feishu/_state/proactive/<bot>/workbench.json`。已获授权规整原文时只更新目标格，先复读比对原值，再写后逐格确认。
   - 凡准备以主人身份发往同事/群聊的回复，写成精准飞书气泡草稿放入 `workbench.json`（含目标群、`@对象`、完整正文、一句话依据、原消息 `applink` 跳转）。
3. `workbench.json` 保管原审批与作者回执，晨间登记的 `outcomes` 为每个业务指定一个最终对象。业务和审批共用一张连续编号的表，下方保留项目日轴。派单归属用 `proactive_dispatch.py overview` 核实。[工作台呈现规范](TASTE-010-proactive-dispatch.md)
   - 消息卡呈收件人、原话或有出处的背景及拟回全文。实名按通讯录或本机已核名册绑定收件账号，称呼依本人指定或历史私聊。主人明确已离职立即退出拟发。本人审稿期间只更新工作台；明确授权具体消息后方可发送并回读。已发原文保留。
   - 扫描近期已交原件、本人决定与作者回执，按稳定的事项键写回原项目轨，保留来源、日期精度与交付版本。每屏约七天，跨周、跨月可滑动；同日节点逐个向下，完整显示名称。点开可查原件与背景、答复人、结论。仅知月份或区间的排期画整段。仍需答复的事项留给原办理人。
   - 每行只交所登记的一条消息、一份文件或一笔审批，工作台自身也绑定固定链接。同件双入口分别核本地原件与线上对象。预览、研究佐证及附件随原件查看。同一业务需要发给两人时按收件人列两行，沿用同一责任人。
   - 主人宣布结束的事项即时退出当前队列。只留匹配该来源和事项的去重键，用 `owner_closed_keys` 阻止原提醒在下一轮重新变成草稿；新事项独立识别。原始扫描继续，普通群消息、旧任务状态与权限核验各留在对应来源，避免替代业务判断。

   主号用私有目录存原始记录、恢复点和预览。执行者完工或遇阻，用当前派单的正常终答回主号，报告成品入口、实测结果、剩余限制或卡点。执行者回报业务验收结论、范围、定量结果和预览。主号按原请求 ID 对账，再更新条目；缺项沿原单补，独立验收另派。跨租户中转也保存目标机实际收到的请求 ID，与回信及同一任务标识关联。

   **向本人交付。** 同批已验成果合成一张私聊交互卡。正文逐项编号，点间留一空行，附原件与待定项。本人直接私聊提问时先给结论和可量化的结果，提案在同一对话给决定点和工作台预览。收到执行者回执或后台完工，使用 `python feishu/proactive_report.py --bot <主号> --batch <稳定批次> --file <私有汇报正文>` 预览，同一命令加 `--send` 才投递。此命令使用绑定本人，核对私聊、真实消息 ID 和卡片类型。同一批次恢复时复用已有记录，失败保留实际状态；不要把群内回执当成本人已收到。迟到结果补进原条目，每日巡检补漏。详见[出站交付合同](SPEC-210-outbound-delivery.md)。
   ```powershell
   python feishu/proactive_scanner.py --bot <bot> --days 7 `
     --actions-json feishu/_state/proactive/<bot>/workbench.json `
     --out-html <业务仓>/docs/proactive-triage-board.html `
     --out-json feishu/_state/proactive/<bot>/latest.json
   ```
   随后按交付规范调用 `$open-local` 在本机打开（若全局在线开关为 `on` 同步发飞书在线版并按 SPEC-210 三行回执）。

### 工作台规范与工具的分工

| 归属 | 唯一职责 | 执行与验收 |
|---|---|---|
| 仓库入口 AGENTS.md / CLAUDE.md | 登记主号、一项业务一位责任人、写入与发送权限 | 入口指向本总流程与对应业务规范。 |
| [通用规范 TASTE-010](TASTE-010-proactive-dispatch.md) | 全台行列、排序、字号与文字、成果命名、空值 | `proactive_business_list.py` 核登记作者及顺序，`proactive_lint.py`、`proactive_business_contract.py` 核布局和字段。 |
| 本总流程 SOP-150 | 收件、排序、派单、取回原件、生成、发布、实点、追单 | 发布前以 `proactive_taste.py workbench` 对照业务登记，`proactive_outcomes.py` 校验每个结果与原件；发布后用本人入口点开同一版。 |
| 各业务 SOP，如[审批 SOP-151](SOP-151-approval-draft.md) | 定义该类业务交付的原件、数据和最后一步 | 审批用 `approval_draft_check.py` 比对保存与重开，另从工作台点验落到同一张单。具体金额、附件与页面证据留在私有回执。 |

[TOOLS.md](../TOOLS.md) 提供命令索引。PLAN 记录这一次的责任、进度与恢复点，原单回执保存实测依据。新业务优先复用已有业务规范，反例加在负责该规则的工具测试中。

**作者在等外部材料。** 主号读完原回执，在 Link16 仓运行 `python feishu/proactive_followup.py --bot <主号> await-input <原单> --receipt <最新回执ID> --condition "<收到什么后可以继续>"`。任务保持开放。后台继续查原单，原作者有新回复时才再次提醒。读取失败会提示查错。本人直接补来材料时，沿原单转交，用 `link` 登记补单。要恢复定时提醒，用 `defer` 设置时间。

### 工作台与业务消息的发布校验

#### 派单、文字与验收的接入方案

**已接入。** `proactive_dispatch.py` 与 `proactive_ownership.py` 核业务、作者和原请求。当前派单仍调用飞书发送。`proactive_followup.py await-input` 可让已审的同一回执保持静默。本机渲染和手机打包都会核对工作台原件。以下是扩展设计，逐个出口通过反例后才算生效。

| 执行入口 | 脚本应该怎样决定 |
|---|---|
| 同机派单 | 把本人原话及附件指针直接投给登记作者，保存原生接收编号后释放主会话。相同原单、业务和需求版本复用接收记录。投递结果不明先查记录；新纠正只沿原单续派。跨机只用已登记的通道。 |
| 健康检查与群消息 | 后台观察作者会话。接收、开工、正常运行只记本机。只有新成品、需要别人解决的阻塞、需要本人决定的事项才通知对应人；明确要求的外发按授权执行。发送前按原单、事件、对象版本和收件人去重，改写措辞不能产生第二次通知。 |
| 计划、权限与验收 | 需求、决定、依赖、排期或恢复点有实际变化才改计划。请求权限前核身份、资源及失败的业务操作。已有权限直接用，缺权限才走对应申请。成品、验收要求和使用环境都相同时复用回执；已确认的线上故障或本人纠正也能触发局部复验。 |
| 人能读到的文字 | 草稿留在私有缓冲区。每条回复、进度卡、群消息在显示或发送前检查；本地文件在替换正式原件前检查；在线文档及工作台在上传或发布前检查最终可见版本。范围包括标题、正文、表格、图注和附件里的说明。复用通过的段落时，核上下文、规则、来源和目标渠道是否仍相同。代码跳过，引用原话核保真。 |

通用写法及改写样例在 [TASTE-010](TASTE-010-proactive-dispatch.md#怎么增加一项可验证规则)。拟从 `proactive_taste.py` 提取共享文字检查，由聊天发送与改卡、文件写入和发布入口调用。新平台或可绕开的直接写入通道要单独登记覆盖。退回时只给作者问题位置、依据和改法，修正后重查；同一失败不在群里来回转发。

**验收。** 先离线回放一批实际消息，分辨哪些成品、故障和决定必须送达。重复消息应拦，真正的新决定须到达。再在主号及工作台试行，分别从各平台的实际聊天、卡片修改、文件保存和发布入口送入好坏样例。核对收件记录及最终文件，确认错误内容未露出、合格内容只出现一次。只有通过的入口计入覆盖。

#### 现行发布检查

1. 在私有业务清单 `morning-business.json` 用稳定业务 ID 登记 `artifact_pairs`（同一 HTML 的 title、local、online）和 `message_policies`（收件人、类别、称呼、原单要点）。
2. 生成与发布前对照原清单逐行核作者、字段、空值、入口数量、标签、实际链接。部署前可独立运行 `python feishu/proactive_taste.py workbench --plan <私有登记.json> --html <待发布工作台.html>`。单件演示的本机入口打开原 HTML，手机展开同一文件的路径，在线入口打开已发布的同一演示。
3. 业务消息和业务回复在确认具体草稿后通过本人发送入口携带 `--business <业务ID>`。在预览与实发前校验同一正文；使用 `python feishu/proactive_taste.py message --help` 可单独预检。未通过时返回原因，修改后再校验。发送授权和对方收件须另有原始回执。
4. 新增规则先给出覆盖对象、可触发失败的反例、判定者。在真实生成与执行入口各运行一次正反例，并复核最终桌面及手机呈现。

## 4. Phase 3：主人确认后执行与回读验真

收到主人明确拍板（例如“表格填进去”“发草稿 #1”“两条都发”）后：

1. **共享表写入**：执行对应脚本加 `--apply`（强制 `--allow-overwrite=false`），写完回读目标单元格确认 100% 落盘且零覆盖。
2. **以主人本人身份发消息**：以下是本机已安装网页发送插件时的用法。缺少插件时保留待发草稿。
   ```powershell
   # 先 dry-run 核对参数
   python feishu/send_as_user_web.py --bot <bot> --target-name "<群名或人名>" --target-type group --chat-id <oc_xxx> --text "<确认正文>"
   # 确认无误后加 --send 执行并自动 OpenAPI 回读验真
   python feishu/send_as_user_web.py --bot <bot> --target-name "<群名或人名>" --target-type group --chat-id <oc_xxx> --text "<确认正文>" --send
   ```
   只有回执 `ok=true` 且 `verified=true`（附真实 `message_id` 与 `message_app_link`）才将同一正文从待发转为已发并刷新工作台。
3. **审批与报销。** 业务作者按[审批 SOP-151](SOP-151-approval-draft.md)核对原件。从工作台一次点开核对账号、单号和表内数据。草稿还须看到原附件与「提交」，在途实例须看到该单当前处理节点。浏览器可能提示确认唤起飞书，此项单独记录。若还需选择草稿或搜索单据，该入口验收失败。主号比对私有点验原件的指纹，仅发布与回执一致的链接，未通过则保留原单、结果格留白。最后提交或审批由本人操作。
4. **约会。** 核本人和每个必要参会人的身份、日期时区和忙闲，按议题与可能追加参会的角色估时、估人数，再查房间地点、容量和可用时段。原主题已有事件则回读复用；主办人与参会名单分别回读，人员和会议室分别检查邀请状态。达不到证据的忙闲状态保持未知。
