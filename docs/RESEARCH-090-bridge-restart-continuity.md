# 飞书桥重启时，工作输出与新消息怎样续接

**`tb24-voiceover` 已在 23:29 载入续传修正，飞书于 23:29:37 确认收到了此前缺失的两张进度卡，随后原卡继续更新。** 首版重启更新引入了“交互提示之后仍在工作的回合被当成完成”的回归，现已修正，原因与验收见下文。正常受控重启保留 Codex 工作和发送确认记录；本次 worker、app-server、观察进程、终端和会话身份均保持不变，没有重新执行视频任务。入站故障窗口仍以实际 SDK 帧、独立进程与原生 Codex 输入确认探针为验证范围。

## 23:29 修正：交互提示之后为何不再发进度

这是 Link16 首版更新引入的错误。22:13 的“余额不足，请充值”和 22:25 的“请选择试听语速”都被观察者输出为答案记录；Codex 在用户回复后继续使用同一个回合编号。新 drainer 在发出答案时把当前回合加入完成列表，后续凡是这个回合的进度都直接跳过，发送位置却照常前进。因此模型还在工作、观察者还在写记录、桥进程也活着，飞书却收不到新进度。最后一条答案回执停在 22:25:18；这是本地丢弃逻辑，不是飞书网络延迟。

现在，答案可以封口当时的卡片，但不能禁止当前回合继续产生新进度。同一回合依靠已发送的事件编号和版本判重：重复快照不再发送，新的公开进度继续发送。完成列表只拦截已经切换到别的回合之后重放的旧回合记录，避免旧进度覆盖新卡。这个判断无需分析回答措辞，也不依赖终端计时文字。

新增回归实际复现了“进度 → 交互答案 → 桥重启 → 同回合新进度 → 再次重放旧记录”：修正前第三张卡缺失；修正后仅发送新的进度，重放不新增卡片。出站及重启相关 46 项测试通过，完整 unittest 回归运行 661 项，结果 OK、其中 1 项跳过。

生产桥 PID 从 48900 更换为 50136 后，观察者正常写入的新快照自动带回未确认的进度；无需回退发送位置、修改确认记录或手动补发消息。恢复预演预计两张卡，真实平台回执也确认两张，随后 23:30 的原卡更新成功；23:30:39 发送位置与 outbox 文件末尾相同。原工作进程 2672、51812、28660、22088 均仍存在。此前验证了重启传输连续性，却漏掉了交互答案的生命周期语义，不能把那些旧测试结果当成该场景已经覆盖。

证据位于 `feishu/_state/focus-20260913/`：`voiceover-recovery-preview.json` 是隔离发送预演，`voiceover-recovery-action.json` 记录没有进行手动快照补投，`voiceover-live-result.json` 保存真实卡片回执与进程状态，`voiceover-regression.txt`、`voiceover-full-suite.txt` 保存本次测试结果。回归用例在 `tests/test_bridge_restart.py` 的 `test_same_turn_continues_after_answer_and_restart_without_repeating_progress`。

## 已经在工作的任务为什么能继续

Codex/app-server、终端和独立观察进程不属于飞书桥进程的生命周期。只替换桥 Python 进程，既不会关闭 wmux workspace，也不会停止模型执行。观察进程继续把用户可见的 commentary、plan 和最终答案写入本地 outbox；桥停着的几秒，输出积存在这个文件里。

桥恢复后，读取保存的发送位置，处理后面的记录。进度卡实际上是普通互动消息的原位编辑，不是必须维持一条连接的 CardKit 流式卡。只要原卡 message_id、已确认的事件版本和回信目标还在，就可以继续改同一张卡。`tb24-voiceover` 的现有状态里确实保存了原卡编号和事件确认记录，并非只有架构注释声称可以恢复。

用户会看到短暂停顿，随后原卡继续更新；长内容达到卡片容量后正常换下一张，最终答案按原有分片规则发送。这里的过程是本来允许公开的进度与说明，不增加隐藏推理的采集或展示。

## 为什么原实现仍不能直接说“随时重启没问题”

原卡信息是在一批发送动作之后才保存；创建进度卡时没有稳定请求编号。因此在飞书已收卡、本地尚未记住卡号的瞬间结束进程，新桥不知道那张卡已存在，会再建一张。

另外，原实现把所有改卡失败都当作旧卡无法继续修改，直接创建替代卡。短暂连接问题也会触发这个分支。卡片状态写入失败又被吞掉，发送位置仍可能前进，重启后无法还原当时的卡片状态。这些都是普通输出流程里能踩到的时间窗口，不能靠“通常不会那么巧”当作保证。

隔离回归先在旧实现运行四个用例：完整保存后重启通过；远端成功但本地确认丢失、临时改卡失败、状态保存失败三个用例失败。随后才修改代码。

## 本次已经修改的行为

新建进度卡先把发送意图落盘：具体正文、目标、每片稳定编号。发送成功立即保存卡号与确认，再继续下一片。重启先恢复这次未结束的操作，再接收更新的进度；即使上一进程没来得及记录成功，仍使用原来的请求编号认领同一次发送。

临时改卡失败保留原卡和待更新版本，恢复后继续改它。只有卡满，或飞书明确告知消息已撤回、编辑次数已用完，才换新卡。保存状态失败不推进发送位置，也不在创建意图尚未保存时发送。旧轮已完成的记录即使重新读到，也不能重开旧卡或封掉新一轮的卡。

原卡编号本身已经定位到聊天，改卡时不再读取下一轮的回信路由来决定是否跳过更新。新桥第一次轮询可以立即处理积存进度，后续更新沿用原合并间隔。长期合同已写入 [SPEC-210 §2.1](SPEC-210-outbound-delivery.md#21-milestone-进度卡跨进程续接)。

飞书对相同 UUID 的请求去重有一小时窗口；它与本地已确认记录长期跳过是两层机制。正常的短时重启由两层一起覆盖。网络请求结果一直不明、超过这个窗口才恢复，或者磁盘损坏、用户撤回卡片，需要单独处理，不能宣称无限期、无条件恰好一次投递。[飞书发送消息接口](https://open.larkoffice.com/document/server-docs/im-v1/message/create)

## 本次验证到了哪一层

最强的用例用了真实的独立进程和本机 HTTP 服务：输出进程单独运行；HTTP 服务先收下进度卡，暂不返回成功；测试立即结束发送进程。没有桥时，输出进程继续写两个新进度。再启动一个全新发送进程，它使用原请求编号接回原卡，将正文更新到第三版，最后只产生一份答案。

服务端共收到两次相同编号的建卡请求，最终只保留一张进度卡和一份答案。这验证的是“同一发送操作的续接”，不是重新执行任务或让用户重发提示词。HTTP 服务模拟了飞书文档定义的请求去重行为；本次没有向真实飞书聊天发测试卡，因此不把该结果说成生产飞书端到端验收。

## 入站为何会丢，以及现在怎样继续

原 SDK 回调把异步处理排进内存便返回；飞书据此确认已经送达，但桥可能还没交给 Codex。本机探针实际观察到“回调已返回、处理函数尚未被 await”。原重启直接结束指定 PID，已被平台确认、仍在内存里的项目没有恢复入口。原 `bridge-inbound` 是历史账本，没有消费状态，查得到日志也不能自动接着做。

现在在原始同步回调里先检查接收权限，再按飞书消息 ID 将正文、附件引用和处理状态写入本地收件箱，磁盘提交成功才返回。实际 SDK WebSocket 帧测试确认：正常保存返回 200；模拟磁盘写满返回 500，没有确认未保存的数据。未授权私聊、群里未 @ 的旁观消息不留存，鉴权头与 token 不写入收件箱。

尚未交给终端的消息继续准备和下载；已完成注入的等待实际输入事件确认，不能再贴一次。`UserPromptSubmit` 是真实会话收到输入时触发的 hook；它匹配本条消息的精确内容摘要，并记录实际 session。即使桥先退出、hook 后到，确认也能独立写入同一收件箱。它不等模型回答，不会把模型网络耗时又搬回收件确认。

附件完成后保存本地路径，恢复时复用已下载文件；同名附件不会互相覆盖。已保存待办不再因 SDK 的“消息太旧”闸被丢弃。准备失败暂缓重试，不挡住后面的 `/stop`；停止指令撤销此前未提交的待办，防止旧任务又跑起来。超长文本落盘失败保留完整待办，不再截断后假装已经交付。

## 正常重启怎样避开交接到一半的窗口

`start` / `stop` 向新桥发送绑定本次进程的停止请求。桥停止领取新待办，等正在进行的这次交接结束，再断开飞书连接退出；模型继续运行。启动器观察到旧进程实际退出后立即启动新桥，并确认服务锁与飞书连接都就绪。180 秒是异常上限，不是正常启动要等的时间，超时也不会强杀仍在交接的新桥。

真实独立子进程测试中，收到停止请求时当前 handler 尚未完成，进程保持存活；放行交接后自行退出，下一条消息仍是 queued。另一个硬退出测试保存附件与 `/stop` 后直接结束进程，新消费者按原顺序读回两条消息。提交边界被强制打断的用例保留 uncertain；收到原消息的后到 hook 才确认完成，全程没有第二次粘贴。

仍有明确边界：任意强杀或断电恰好发生在不可查询的斜杠/TUI 副作用中间，且真实接收记录也没留下，无法自动证明“做了还是没做”。此时保留结果不明记录，不盲目重做。正常受控重启通过等交接完成避开窗口，不声称任意时刻、无条件恰好执行一次。
