### 0.3 概念地基：slash 命令 / skill / command / CLI 到底是几层东西

> 主人明确提到「一直没有好好解释清楚这些概念」。这一节不是科普——**它直接决定了本方案的形态**
> （看门狗到底能不能「发一个 `/close`」）。

一共**四层**，它们的差别是**「谁执行这句话」**：

| 层 | 例子 | 谁执行 | 从哪触发 | 看门狗能用吗 |
|---|---|---|---|---|
| **① 桥的 slash 命令** | `/close` `/account` `/cd` `/screen` `/stop` `/new` `/clear` `/help` | **飞书桥进程**（`feishu_bridge.py` 的 `handle_slash`） | **只能从飞书消息进来**——桥在把消息注进面板之前拦下它 | ❌ **不能**。看门狗不是飞书消息来源 |
| **② agent 自己的 slash 命令** | `/status` `/usage` `/resume` `/model` `/login` | **Claude Code / Codex 这个 CLI 程序自己** | 面板里敲，或桥**原样透传**进去 | ⚠️ 能注进面板，但结果只显示在屏上，脚本拿不到结构化数据 |
| **③ skill** | `/feishu` `/align` `/find-session` | **模型自己**（读一份 `SKILL.md` 的指令照做） | agent 会话里 | ❌ 不是代码，没有会话就没有它 |
| **④ CLI 脚本 / 库函数** | `feishu/send_feishu_msg.py`、`agent_runtime.persist_account()`、`wmux_session.close()` | **Python 解释器** | 任何进程，随时 | ✅ **这是看门狗唯一能用的层** |

**所以本方案的形态被这张表钉死了**：看门狗**不能**「发一个 `/close`」，也**不能**「发 `/account ccp`」——
那两句只有从飞书进来才被桥认识。它能做的是**调用 `/close` 和 `/account` 背后调的那些函数**。
好消息是这条路**已经有人走通了**：`feishu/bridge_cron.py` 就是一个外部进程，它靠
`import feishu_bridge as fb` + `fb.ensure_session()` + `fb._inject()` 给任意 bot 派活。
本 plan 完全复用这条既有路径，**不发明新的控制通道**。

至于 `/status`（②层）：主人设想「发 `/status` 去问它现在用哪个号、session id 多少」。
**不需要**——这些信息桥已经结构化地写在 `feishu/_state/bridge-session-<bot>.json` 里了
（`profile` / `pty` / `workspace_id` / `jsonl` / `cwd`），直接读文件即可，比读屏准。

## S2 · 撞 limit 看得见：检测 + 飞书 DM 告警 — [ ]

> **主人原话：「我在飞书上没有任何的通知，这个是很致命的事情」。本 stage 优先于换号与接手** ——
> 先让它**看得见、说得出**，再谈自动处理。看得见但不自动处理，主人还能自己动手；
> 看不见，自动处理做得再好也没人知道它做没做。

### S2.1 limit 的判据（屏 + API 双源交叉）
1. **解决什么问题**：现在的 `find_pane_error()` 对限流完全失明（S0.2 事实 1 实测）。
2. **矛盾点**：**只读屏不够**——屏是滚动的，那句 limit 提示会被后续输出挤出读窗（当前只读 25 行）；
   **只读 API 也不够**——API 只知道「这个号满了」，不知道「哪个面板正卡着」，
   而一个号可能同时挂着好几个 bot、有的在跑有的闲着。
3. **推荐方案**：**两把尺子都要，且分工明确**：
   · **屏**负责回答「**是哪个面板**撞的」——正则认 `hit your (weekly|usage|session) limit` /
     `limit reached` / `/usage-credits` / `resets? (at|in) `；
   · **API**负责回答「**这个号是不是真满了**」——`agent_quota` 判定 == `满`。
   **两者都成立才判定限流**。只有屏命中而 API 说没满 → 记一笔但不动手（可能是历史残留文字）；
   只有 API 满而屏没命中 → 也不动手（该号名下的会话可能压根没在用）。
   这条「双源」正是为了避开本仓反复吃亏的「尺子坏了但输出正常」。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 新增纯函数 `find_pane_limit(text)` +
   判定函数 `is_limited(pane_text, quota_row)`；**不动**现有 `find_pane_error` 的语义（那是另一件事）。
5. **交付物**：两个可单测的纯函数 + 一张「屏命中 × API 满」四格真值表。
6. **验证**：喂 voiceover 撞限流当天的真实屏文本 → 判 True；喂它 15:02 那次 `API Error` 的屏 → 判 False
   （那是 API 错不是限流，该走原来的注「继续」而不是换号）。

### S2.2 告警改走 bot 自己的 DM
1. **解决什么问题**：告警现在发进 xhs 的自定义机器人 webhook，主人在 DM 里零可见（S0.2 事实 3）。
2. **矛盾点**：webhook 有一个真优点——**桥挂了它照样发得出**（不依赖桥进程）。
   全改成走桥，等于把「桥自己死了」这个最需要报警的场景的通道也砍了。
3. **推荐方案**：**双通道按病因选路**（沿用 PLAN-931 S3.3 已定的原则）：
   · 会话级事件（撞限流 / 换号 / 接手）→ `feishu/send_feishu_msg.py --bot <该bot>` →
     **落在主人与那个 bot 的 DM 里**，带 `route=p2a` 信封。**用哪个 bot 发就等于说明是哪条线**，
     主人不用猜。
   · 桥级事件（桥进程没了）→ 退回 webhook。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的通知函数（两条路径 + 一个选路判据）。
5. **交付物**：两条通知路径 + 书面选路规则。
6. **验证**：真发一条到主人 DM 并由主人确认收到；再模拟桥挂，验证退回 webhook 仍送达。

### S2.3 五类事件的文案与冷却
1. **解决什么问题**：主人要的是「像重投消息那样的提示」——**能一眼认出发生了什么**，不是一堆日志。
2. **矛盾点**：看门狗每 120 秒轮询一次，一个号满了会**连续满好几个小时**；
   不做冷却 = 每 2 分钟一条轰炸；冷却太狠 = 换号成功这种关键事件被吞掉。
3. **推荐方案**：**按事件类型分别定冷却**，而不是一刀切：
   · `撞限流`（状态类·会持续成立）→ 每 bot **30 分钟**最多一条；
   · `已换号` / `已接手` / `换不了`（动作类·一次性）→ **不冷却，必发**；
   · `已恢复`（一次性）→ 不冷却，必发。
   状态类冷却记在 `feishu/_state/watchdog-alerts.json`（与 `bridge-session-` 同款命名法，不新建目录）。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `notify()` + 一个 `_alert_gate()`。
5. **交付物**：五类文案模板 + 冷却表。
6. **验证**：模拟同一 bot 连续 20 轮都满 → 只发出 1 条；其间插一次换号成功 → 那条立刻发出不被吞。

### S2.4 文案内容（发什么才叫「有用」）
1. **解决什么问题**：一条只说「limit 了」的消息，主人还是得自己去查是哪个号、什么时候恢复。
2. **矛盾点**：信息给全会很长，飞书 DM 里看着累；给太少等于没给。
3. **推荐方案**：**一条消息回答四个问题**，一行一个，不超过 6 行：
   谁卡了（bot + 目录）/ 哪个号 + 撞的是周还是 5h / 什么时候恢复（北京时间）/ 我打算怎么办。
   例：`🔴 tb24-voiceover 撞限流｜账号 ccp2 · 周额度 100%｜08-21 18:00 恢复｜候选 ccp(周13%)，正在切`。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的文案常量。
5. **交付物**：五条文案模板。
6. **验证**：主人看一眼就能判断「要不要我插手」，不用追问。

## S4 · 自动换号 — [ ]

### S4.1 换号的原子步骤
1. **解决什么问题**：主人手上的 `/account ccp` 是一条飞书命令，脚本发不出（§0.3）。
2. **矛盾点**：`/account` 的处理函数里有一步是**改桥进程内存里的 bot 字典**
   （`apply_account(bot, al)`）。外部进程改得了名册文件，**改不了别人进程的内存**——
   只写文件的话，跑着的桥下次冷启**仍会用旧 profile**，等于白切。
3. **推荐方案**：**用「重启那一个 bot 的桥进程」代替「改它的内存」**。完整顺序：
   ① `agent_quota.pick()` 选号 → ② DM 播报「要切了」 →
   ③ `agent_runtime.persist_account(bot, target)` 写名册 → ④ `wmux_session.close(ws)` 关旧会话 →
   ⑤ `feishu_bridge.py stop --bot X` 然后 `start --bot X`（新进程**必然重读名册**） →
   ⑥ `fb.ensure_session(bot)` 在新号上冷启 → ⑦ 注入接手 prompt → ⑧ DM 播报结果。
   **③ 之后每一步失败都要 DM 报出来**，绝不静默。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `failover()`；不改桥的 `/account` 逻辑（它照常服务主人）。
5. **交付物**：一个八步、每步有日志与失败播报的换号函数。
6. **验证**：换完后 `bridge-session-<bot>.json` 的 `profile` == 目标号，
   且新会话的 transcript **真的落在目标号的 home 下**（这是唯一能证明「真的换了号」的证据，
   光看名册文件不算——名册是我们自己写的）。

### S4.2 选号规则
1. **解决什么问题**：主人给的规则是「claude 满了先换另一个 claude，都不够再上 codex」。
2. **矛盾点**：跨 runtime 换（claude → codex）**不只是换个号**——Codex 是另一个 agent，
   它的 skill 触发方式、hook、回传路径全不同，接手同一份 Claude transcript 的效果**没有验过**。
3. **推荐方案**：**同 runtime 自动、跨 runtime 先问**。
   `pick()` 已实现三条有序规则（排除刚撞的 → 同 runtime 优先 → 余量大优先）。
   若选出来的是**另一个 runtime**，则**不自动切**，改为 DM 问主人一句
   「claude 两个号都满了，切到 cxp(codex) 吗？回『切』我就切」。
   —— 这条是 §3 待主人拍板的问题之一，默认取保守值。
4. **改什么·改哪里**：`feishu/agent_quota.py` 的 `pick()`（已有）+ `bridge_watchdog.py` 的跨 runtime 闸。
5. **交付物**：选号规则表 + 跨 runtime 的人工确认闸。
6. **验证**：造三种额度组合（另一个 claude 够用 / 只剩 codex / 全满），各走对分支。

### S4.3 换号的闸（防止把事情搞更糟）
1. **解决什么问题**：自动换号是**有破坏性**的动作（会关掉一个正在工作的会话）。
2. **矛盾点**：闸太松 → 抖动一次就换号，把好会话关掉；闸太紧 → 真撞限流时不动，等于没做。
3. **推荐方案**：**四道闸，全部满足才换**：
   ① 双源判定成立（S2.1）；② 该面板**连续 2 轮静止**（沿用 xhs 那道 `ERROR_STUCK_CONFIRM`，
   避免它其实还在用 usage-credits 继续跑）；③ 该 bot **24 小时内自动换号 < 2 次**；
   ④ 目标号 `verdict` ∈ {够用, 紧张}，**`问不到` 绝不选**（宁可不换，也不换到一个不知深浅的号）。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `_failover_gate()`；计数记在 `watchdog-alerts.json`。
5. **交付物**：四道闸 + 每道闸被挡下时的日志理由。
6. **验证**：逐道闸单独造反例，验证各自都能独立拦下（**每道闸都要先证明它会拦**，否则等于没装）。

## S5 · 任务接手 — [ ]

### S5.1 交接包：从哪拿「原会话是谁」
1. **解决什么问题**：新会话得知道「我要接的是哪一段活」。
2. **矛盾点**：主人的设想是「复制最后 50 行 / 复制 session id 让它去 `find-session`」——
   但 `find-session` 是**跨全机搜 jsonl**的重活，而这里其实**根本不用搜**。
3. **推荐方案**：**直接读桥已经写好的结构化指针**。
   `feishu/_state/bridge-session-<bot>.json` 里现成有 `jsonl`（transcript 绝对路径）、
   `profile`、`cwd`、`workspace_id`。**在关掉旧会话之前先把它快照下来**（关了就没了），
   存成 `feishu/_state/watchdog-handoff-<bot>.json`。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `snapshot_handoff()`，在 S4.1 第 ④ 步**之前**调用。
5. **交付物**：一份交接包 JSON（旧 profile / transcript 路径 / session id / cwd / 撞限流时间 / 屏尾 50 行）。
6. **验证**：拿 voiceover 现场跑一次，交接包里的 transcript 路径能被打开且非空。

### S5.2 接手 prompt 契约
1. **解决什么问题**：主人已经把想说的话说清楚了，要把它固化成模板，不用他每次重打。
2. **矛盾点**：transcript 可能**极大**（voiceover 那份实测 **145 MB / 14140 行 / 750k tokens**），
   叫新会话「认真读完」会当场把新号的上下文也撑爆——**用一次限流换来另一次限流**。
3. **推荐方案**：prompt 里**明确规定读法**，不许通读：先读**尾部**（最近 N 条）定位「停在哪」，
   再按需回溯，**禁止一次性读整份**。并把「不用跟我确认、不用对齐、直接接着推」写死进模板
   （这是主人反复强调的）。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的 `HANDOFF_PROMPT` 常量（中英两套，语言检测沿用 PLAN-931 S3.4）。
5. **交付物**：一份接手 prompt 模板。
6. **验证**：真跑一次接手，新会话在**没有额外提示**的情况下说得出「原任务是什么 / 做到哪 / 接下来干什么」。

### S5.3 后台任务的交接（最容易漏、且实测有坑）
1. **解决什么问题**：撞限流的会话常常**挂着后台长跑任务**（主人点名的「后台还有三个 shell」）。
2. **矛盾点**：**后台任务的句柄是会话私有的**——Claude Code 的 `bash_id` 只在原会话里有效，
   新会话**拿不到、也 kill 不掉**。而这些进程是 `nohup … &` 起的，**关掉面板它们照样活着**。
   于是必然出现「新会话不知道有它们，旧会话已经没了」的孤儿。
3. **推荐方案**：**交接包里带上 OS 层面的证据，让新会话用进程表而不是句柄去认领**：
   快照时记下该 cwd 下的相关进程（pid / 命令行 / 启动时间 / 已烧 CPU）+ 相关日志的 mtime，
   prompt 里明确要求：**先确认这些后台任务是活的、卡死的、还是已完成的，再决定接着等还是重起**。
   （voiceover 现场实测：4 对 `render-p002.sh` 还挂着，但每个只烧了 5-28 秒 CPU——
   而一次真渲染要烧 ~1669 秒，日志两小时没长 ⇒ 它们是**卡死的孤儿**，不是在干活。
   **光看「进程还在」会得出完全相反的结论**，所以必须带上 CPU 与日志 mtime 两个佐证。）
4. **改什么·改哪里**：`snapshot_handoff()` 增加进程扫描段；prompt 模板增加「后台任务」一节。
5. **交付物**：交接包里的后台任务清单（含死活判据）。
6. **验证**：拿 voiceover 现场生成一次，清单里 4 对 render shell 都在，且被标成「疑似卡死」。

### S5.4 原号恢复之后
1. **解决什么问题**：ccp2 到 08-21 18:00 就满血复活了，那时该怎么办。
2. **矛盾点**：自动切回去 = **又一次打断正在干活的会话**（这次还是被我们自己搬过去的），
   完全不管 = 主人失去「资源回来了」的信息。
3. **推荐方案**：**只播报、不自动切回**。恢复时发一条 DM「ccp2 已恢复（周 0%）」，
   要不要切回由主人一句 `/account ccp2` 决定 —— **打断的代价必须由人来付**。
4. **改什么·改哪里**：`feishu/bridge_watchdog.py` 的恢复检测 + 一条播报。
5. **交付物**：恢复播报 + 明确写下「不自动切回」的理由。
6. **验证**：把某号的记录状态改成已满再改回，验证只发一条播报、不动任何会话。

### S6.2b 验收里必须有「名册命中活面板数 > 0」这一维（tb25-link16 2026-08-20 建议 · 采纳）

2. **矛盾点**：这一维看着像「测别人家的东西」（名册是桥写的），容易在验收表里被认为不该管。
