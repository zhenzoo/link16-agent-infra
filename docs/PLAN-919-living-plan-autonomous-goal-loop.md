**B2 · 交付物声明 + 「途中随手发」约定**
- **解决什么**：主人要「每个 stage/step 到底交付什么」写清，且交付物**途中发**（不停下等 check）。
- **矛盾点**：align 的交付契约已要求「每步写交付物」，但没写「**中间交付物（链接/页面）什么时候发**」→ agent 容易憋到最后、或停下等确认。主人明确：**途中发、别停**。

### Section C · living-plan 长跑自主（/goal + /loop + 停机红线）

**C1 · 新增「长跑机制」节：/goal 主驱 + /loop 辅 + auto mode**
- **解决什么**：给 living-plan 补上**跨轮续跑的实际机制**（现在只有纪律、没机制 → agent 结束 turn 就停）。
- **矛盾点**（本 plan 最该讲透）：主人说「/goal 和 /loop 都用上」，但两者**用途不同、不能混**——`/goal`=干到 plan 完成（正驱动），`/loop`=轮询等外部（辅助）。若不分清，会拿 /loop 去驱动多步 plan（它重跑同一 prompt·丢进度）→ 更糟。
- **推荐方案**：新增一节明写**分工**：
  - **主驱 = `/goal <可观测完成条件>`**：如 `/goal "PLAN-NNN 所有 stage 打✓、验收测试全过"`——agent 每轮做下一 step、小模型判达成没、没达成自动开下一轮、达成才停。**这是"一路跑到完"的正解。**
  - **辅 = `/loop`**：仅用于 stage 内**等外部异步**（CI 在跑 / 部署中 / 远程队列）——到点轮询查状态，查到就继续。**不拿它驱动 plan。**
  - **auto = 主人现有 `--dangerously-skip-permissions`**：它已等价「turn 内不弹权限框、自动批准」→ **够用、不用额外设 auto 模式**（评估见 §3-Q2）。它管"turn 内不停手"，`/goal` 管"跨轮续"，两者配合 = 真·长跑。
- **化解矛盾**：一句话分工（goal 驱动 / loop 等外部 / dangerously 免打断），主人「都用上」的意思落地、且不误用。
- **改哪里**：`living-plan/SKILL.md` 新增「§7 · 长跑自主执行（/goal 主驱 + /loop 辅）」节（约 +12 行）。
- **交付物**：living-plan 新增 §7。
- **验证**：cheap（起一个小样任务·`/goal` 真跑一遍·看它是否跨轮自动续到达成·不用人喊「继续」）。

**C2 · 两条停机红线（收紧现有「停机条件」）**
- **解决什么**：把主人的两条红线写死，替掉现在泛泛的「由上游指令定」。
- **矛盾点**：living-plan §6.5 说「停不停由上游指令定」——但主人这次给了**明确的默认红线**：默认**一路不停**，只有两种才停。这不是"上游每次都要说"，而是**默认行为**该改成"不停"。
- **推荐方案**：living-plan「停机条件」改为**默认长跑 + 两条硬红线才停**：
  1. **重大架构偏差**——执行中发现「实际情况和 align 时讨论的**不一样、会推翻/大改**方案」→ 停下报主人、等拍板。

  - 其余（普通 bug、找不到文件、方案取舍、一个 stage 做完）**一律不停、继续冲**。
- **化解矛盾**：默认"不停"写死，两条红线清晰可判，agent 不再动辄停。
- **改哪里**：`living-plan/SKILL.md` §「自主执行·停机条件」重写（现有那节·约改 5 行）。
- **交付物**：停机条件新版（两条红线）。
- **验证**：none（文档）+ 并入 C1 的小样 e2e（看它遇到普通 bug 会不会误停）。

**C3 · 「别中途结束 turn」纪律强化**
- **解决什么**：治 phd-taoci-3 那种「嘴上说继续、却结束 turn」。
- **矛盾点**：即便有 /goal 兜底（结束了会被重新唤起），但每次结束→重启有开销、也让主人看着像"停了"。最好 agent **本来就别在 plan 中途结束 turn**。
- **推荐方案**：living-plan §7 加一句硬纪律：「**plan 未完成前，绝不用『我埋头做/稍后发你』这种话结束本轮** —— 要么这一轮就把下一 step 做了，要么(等外部)挂 /loop，`/goal` 只当兜底安全网、不当"正常停手的借口"」。
- **化解矛盾**：/goal 是安全网、不是偷懒理由；agent 主动连做，减少空转重启。
- **改哪里**：`living-plan/SKILL.md` §7（并进 C1·约 +2 行）。
- **交付物**：§7 的纪律条。
- **验证**：并入 C1 小样 e2e。

## §3 · 请主人拍板

**Q1 · `/goal` 的完成条件怎么写成「可观测」？** `/goal` 靠一个**小快模型**每轮判「达成没」，所以条件要写成**它能核的硬事实**（"测试过"而非"代码好"）。我推荐：**plan 文档里每个 stage 一个可勾选标记**（`- [ ] S1 …` / 做完回填 `- [x]`），`/goal` 条件 = 「PLAN-NNN 所有 stage 打 [x] 且验收通过」。这样小模型读 plan 文档就能判。**同意用这个「勾选标记」当完成信号吗？**

**Q2 · auto 模式 = 你的 `--dangerously-skip-permissions` 够用吗？** 我评估：**够用**——它已经让「turn 内所有工具调用不弹权限框、自动批准」，等价于 auto 模式在"免打断"这件事上的效果（甚至更彻底）。`/goal` 负责"跨轮续"。所以**不用再额外设什么 auto 模式**，你现有的 `--dangerously-skip-permissions` + `/goal` 就是完整的长跑组合。**认可吗？**（⚠️ 它绕过所有权限含危险操作·你一直这么用、知道风险。）

**Q3 · `/loop` 就限定「等外部异步」用（不驱动 plan），对吗？** 我推荐 `/loop` 只用于「CI/部署/远程队列在跑，到点轮询查」这类**等外部**场景；**驱动多步 plan 一律用 `/goal`**（/loop 重跑同一 prompt 会丢进度）。**这个分工可以吗？**
