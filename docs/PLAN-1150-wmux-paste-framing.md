本轮推荐：在现有 Codex TUI 网关转发原生请求前展开全文。飞书原文先进入现有可靠收件箱，终端只送消息专属短标记；网关按 bot/profile/startup/thread/mid 的绑定从收件箱取回完整正文，把它放入原 turn/start 或 turn/steer 的 text 输入，随后仍由原会话处理。文件或数据库只作内部可靠运输；Codex 用户消息必须是真正文，不能把标记或文件路径送给模型，也不另开业务会话。优先复用消息级 inbox，不能用只保存最近一条的 last_prompt 处理多条排队消息。

长度策略：换行和 TAB 不再决定用户是否失去聊天正文；字数阈值只用于真实容量与显示折叠。原 16000 是 Windows 命令行参数预算，不是 Codex 正文上限，换成 WebSocket 内 JSON 后不能沿用作截断依据。单请求实际容量和上下文预算仍需隔离压测；离线 60000 UTF-16 单元通过不代表生产支持上限。超过经验证容量时保留待办并明确说明，不能静默截断、转成 TXT 索引或拆成多个会自行执行的用户回合。

路线取舍：只调终端长度阈值不能消除 10 字编号行误判，也不能解决旧试验标点丢失；另开原生输入连接虽可避开终端，但会另行承担忙时追加、TUI 同步、一次性 effort 和回执关联，当前网关已有请求入口，因此不优先。网关展开保持现有会话与交互通道，但必须通过下列门槛，不能因离线成功就上线。

接入与验收边界：①现有 codex_startup.TuiGateway 仅对 turn/start 调 turn_modifier，须增加独立的正文转换覆盖 turn/steer，再仅对新回合应用既有 effort，保留 expectedTurnId/clientUserMessageId、图片等非正文输入；不能把旧标记的 text_elements 偏移留给展开后的正文。②feishu_bridge/bridge_inbox 须登记完整 canonical prompt 与原 mid/route，按同一正文确认消费；现有 prompt_digest 会规范换行/strip，不能作为逐字保真校验，应另以原 UTF-8 字节校验。③短标记必须唯一且绑定当前 profile/startup/thread；缺材料、摘要不符、串会话、混有手写草稿均在上游请求前拒绝，不发送索引兜底。④正文展开发生在模型收到请求之前，用户输入 hook、工作行和回址应看到完整原文及相同信封；摘要/接受回执不等于持久化完成，未确认状态先按 mid 和完整正文查历史，禁止盲重投。⑤真机同时核原生 userMessage、持久化后恢复回读、当前 TUI 的即时全文显示，确认不留短标记、不重复消息；保留 clientUserMessageId 仅是必要接入信息，尚无证据证明它自动修正 TUI 乐观显示。⑥空闲/忙时补充/排队/拒绝/断线后结果不明均测，真实审批仍由原通道处理，不绕过权限。

平台边界与证据：本机 Claude 2.1.309、Codex 0.163.0、Kimi 2.3.1。上述推荐针对已有 Codex TUI→app-server 网关；Claude/Kimi 没有这一现成接入点，继续保留现行保护，待各自原生输入与历史能力核验后再设计，不能声称三平台已解决。[OpenAI 官方协议](https://learn.chatgpt.com/docs/app-server)列明 turn/start/turn/steer 的 text 输入与 userMessage；本机 0.163.0 生成的 schema 也支持两种输入及 thread/items/list。二者证明接口存在，不证明当前产品端到端已通过。

当前 Step／恢复点：全部完成。Stage 1–2 是文件交接历史，Stage 3 仅为调研且不再实施；最新最小修复已删除 `_prepare_tui_text` 的换行触发条件。入站定向 31 项通过，全仓 1276 项、155 个子用例通过；未重投历史消息。
