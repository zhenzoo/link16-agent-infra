# PLAN-980 · 无 drive:drive 时的飞书在线文档收发通路

> 本 PLAN 保留无 `drive:drive` 的实验账本。当前生产选择已由 [PLAN-990](PLAN-990-tenant-and-document-delivery-simplification.md) 收敛为同一 bot 的 `send --doc`：Markdown/TXT 原生 docx 优先，在线失败发原文件附件；本文件早期的跨 bot relay 候选不再是运行策略。

## 0 · 结论先行

**主人的前提有一处不成立，而这处不成立正是出路所在。**

- ❌ 以为：「智能体连读文档的权限都被卡住了」。
- ✅ 实测：`tb26-baseball` 缺的**只有 `drive:drive` 一条**；`docx:document`（读 + 写 + 创建）+ `docx:document.block:convert` 全都有。
- ✅ 实测：bot 用自己的身份**已经能读群里所有在线文档**（6/6 篇，含 wiki，最大一篇 33,395 字），一条新权限都不用开。
- ✅ 实测：**同一个租户里 `drive:drive` 是批过的** —— `tb26-link16` 和 `tb26-multi-camera` 都有。所以这不是租户级禁令。

所以真正被卡住的只有一件事：**bot 建出来的文档，它没法分享给主人**（加协作者 / 设公开链接都要 `drive:drive` 系列权限）。绕开这一件事，就全通了。

**推荐路径（今天就能上线）**：`baseball` 负责写内容 → **`tb26-link16` 代发**（同租户、已有 `drive:drive`）→ 生成在线文档链接 → `baseball` 把链接发给主人。已端到端跑通，见 §1 证据 E8/E9。

## 4 · 推荐路径

> **2026-08-27 定稿修订**：本节前两版把「代发」当主线，那是**在一只权限没开齐的 bot 上做判断**得出的错误结论。
> `publish_text_as_doc` 跑通后，代发与附件降级**双双作废**，正常流程就是主线。

**主线（发）= `publish_text_as_doc` docx 原生发布** —— 建文档 → markdown 转块 → 普通块批量写 + 表格逐格建 → 设可读范围。
只用 `docx:*` 权限，**不需要 `drive:drive`，不需要任何需审核权限**。`tb26-baseball` 零高权限实测跑通（E31）。

**主线（收）= blocks 拉取 + `im:resource`** —— 文档正文/结构逐字可取；群里的图片文件音视频原始二进制直接落盘。
文档内嵌图片再加一条 `docs:document.media:download`（E27 已实测可开）。

**已作废，不要再用**：
- ~~L1 代发（借有 `drive:drive` 的 bot 发布）~~ —— 主线通了就没必要，且会让文档 owner 张冠李戴。
- ~~附件降级（发原始文件代替在线文档）~~ —— 同上，且降低可读性。

**仍然保留、但用途不同的**：
- **L4 自建 Cloudflare Pages** —— 不是兜底，是**唯一能做到「免登录公网可看」的路径**（E25/E26）。飞书文档永远要求登录。
- **L2 OAuth 主人身份** —— 只在「文档要归主人所有」或「要读 bot 看不到的私有文档」时才有价值，优先级已降。

### 4.1 我 与 豆包 的分工（两全其美的具体形态）

| 能力 | 豆包（工作版） | 我（Link16 bot） | 谁上 |
|---|---|---|---|
| 读 docx / wiki | ✅ 实测 3 篇 | ✅ 实测 6/6 篇，最大 33,395 字 | **我**（平手，但我能落地成文件） |
| 读 bitable 多维表格 | ❌ E14 | ❌ 无 scope | **都不行** → R7 |
| 读 sheets 电子表格 | ❌ E14 | ❌ 无 scope | **都不行** → R7 |
| 搜通讯录定位到人 | ✅ 秒找到 open_id | ❌ 受限 | **豆包** |
| 翻主人与他人的会话记录 | ✅ 翻出 5 条链接 | ❌ 只能读我在的群 | **豆包** |
| 读本机文件 / 建工具 / 跑脚本 / 发布 | ❌ E15「和你的本地隔离」 | ✅ 全量 | **我** |
| 把内容变成在线链接给手机看 | ❌ | ✅ E8/E9 | **我** |

**交接约定**：需要豆包时，主人在豆包那边问一句、把结果贴给我；我负责把它落成文件、查证、发布。**不做「我自动去 @ 豆包」** —— 那要赌它理不理机器人的 @，而它能带来的增量（触达面）恰恰是主人一句话就能替代的，不值得为此建一套脆弱的自动链路。

> **补充（2026-08-26 20:05）**：主人提出的真实需求不是「要豆包的总结」，而是**要原始数据一字不落**。E16/E17 证明这条路我自己就能走通（见 §4.3），豆包的转写反而是**降级品**。所以 R4 的定位再收窄：**只在「某份内容我连读都读不到」时才用它当人肉转述**，永远不作为原始数据来源。

### 4.2 企业号 vs 个人号 · 实测能力矩阵

主人的问题：既然电脑是我的、内容也是我处理，为什么非要挂企业账号？下表全部实测，不含推测。

| 能力 | 企业租户 bot（tb26 · `YOUR_TENANT.feishu.cn`） | 个人租户 bot（tb25 · `my.feishu.cn`） | 证据 |
|---|---|---|---|
| 读公司群消息 | ✅ 49 条历史全读到 | ❌ **进不去公司的群** | E5 |
| 下载群内别人发的图片/文件原文 | ✅ 4/4，最大 240KB | ❌ 同上 | E17 |
| 读公司在线文档 / 知识库 wiki | ✅ 6/6 篇，最大 33,395 字 | ❌ **`forBidden` 硬墙** | E3 / E5 |
| 同事能不能直接 @ 它、把活派给它 | ✅ 已在「对外群B」（7 人） | ❌ 同事根本加不到 | 群列表 |
| 建在线文档 + 分享 + 内嵌图片 | ✅ link16 / multi-camera 全通；baseball 缺 `drive:drive`（可代发绕过） | ✅ 全通 | E8 / E16 / E18 |
| 新权限怎么开 | ❌ **要企业管理员审批**（baseball 就卡在这） | ✅ **你自己就是管理员，秒批** | 主人经历 |
| 文档归属与协作 | 在公司云空间，同事可协作 | 只在你个人空间，同事看不到 | E18 |

**结论：这不是二选一，两边是互补的，而且换成个人号会直接丢掉你现在正在做的事的原料。**

- E19 显示你近期用 baseball 做的是 TC101S PRD、高深的文档、群里的用户访谈记录和图片 —— **这些个人号一条都读不到**（E3 的 `forBidden` 是硬墙，不是配置问题）。
- 而企业号的那个缺口**是「单只 bot 没批下来」，不是「企业租户不给」** —— 同租户的 link16 和 multi-camera 都拿到了 `drive:drive`（E2）。
- 所以对「企业号能不能做到和个人号一样的效果」这个问题：**能，已经做到了** —— L1 代发通路（E8/E9）就是答案，本 plan 自己就是这么发出来的。

**个人号的缺点（也要列全）**：① 读不到任何公司内容 ② 同事接触不到 ③ 你在手机上要切账号才看得到它发的文档 ④ 公司内容如果被搬到个人租户，等于把公司资料挪出企业管控范围，是**合规风险**，不建议。

**建议形态**：企业号当主力（公司内容 + 同事触达 + 发文档走代发）；个人号保留为「不碰公司内容的私活 + 需要秒批新权限时的试验田」。

### 4.3 原始数据可达性矩阵（主人真正要的东西）

主人明确：要的是**原始数据一字不落**（文档全文、图片、音频、视频），不是任何人的总结。实测现状：

### S1 · 代发通路：让 baseball 立刻能发在线文档 `- [ ]`

**S1.1 建 `feishu/doc_publish_relay.py`**
- ① 解决什么问题：无 `drive:drive` 的 bot 发不出在线文档链接，只能把几千字 plan 糊在对话框里。
- ② 矛盾点：既要「谁写内容谁署名」，又要「谁有权限谁发布」—— 两者在飞书里是同一个身份，拆不开。
- ③ 推荐方案：**身份与权限解耦**。发布器接受 `--author-bot`（内容归属）和自动选出的 `--publisher-bot`（有 `drive:drive` 的同租户 bot），文档标题带作者 bot 名，链接由作者 bot 发出。化解在于：主人只 care「谁给我的、内容对不对」，不 care 云文档的 owner 字段。
- ④ 改什么·改哪里：新建 `feishu/doc_publish_relay.py`；从 `bridge_scope_audit.capability_status` 实时选出同租户里 `docs-import` 为 ready 的 bot 当发布器，选不到就报错并给出 §3 的降级建议。
- ⑤ 交付物：1 个脚本 + `TOOLS.md` 一行登记。
- ⑥ 验证：baseball 身份跑一次，拿到链接，量 M1 / M2 / M8。

**S1.2 接进 `feishu_bridge.py send --doc`**
- ① 解决什么问题：现在这条命令对无权限的 bot 直接失败，agent 只能放弃、改把长文糊进对话框。
- ② 矛盾点：不能为了兜底就让所有 bot 都改走代发（那会让文档 owner 全变成 link16，日后难追溯）。
- ③ 推荐方案：**只在自己发不了时才代发**。先按原路走，遇到 `99991672` 才触发 relay，回执里写明「本篇由 X 代发」。
- ④ 改什么·改哪里：`feishu_bridge.py` 的 `send --doc` 分支加 fallback；回执增加 `published_by` 字段。
- ⑤ 交付物：1 处改动 + 回执字段。
- ⑥ 验证：baseball 与 link16 各发一篇，回执分别显示代发 / 自发。

**S1.3 隐私档位开关**
- ① 解决什么问题：现在默认 `anyone_readable` = **互联网上任何人拿到链接都能读**，企业租户A 的内部内容这样发有泄露风险。
- ② 矛盾点：公网可读 = 手机上最省事（不用登录、任何账号都能开）；组织内可读 = 安全但要求用对账号登录。

- ⑤ 交付物：2 个预设 + 1 个开关。

### S2 · 下载通路：在线文档 → 本地 Markdown `- [ ]`

### S3 · 主人身份通路（OAuth）`- [ ]`

**S7.1 建 `feishu/feishu_raw_pull.py` —— 一条命令把任何飞书对象扒成本地原始档**
- ① 解决什么问题：现在文字、图片、文件散在三套不同 API 里（`docx/blocks`、`im/resources`、`drive/medias`），每次都要现写代码。
- ② 矛盾点：三套 API 的权限模型不一样（文档看组织可见性、聊天媒体看我在不在那个会话、文档内嵌图看我是不是协作者），统一封装容易把「拿不到」偷偷吞掉变成空文件。
- ③ 推荐方案：**统一入口、分别记账**。输入任意飞书链接或消息 id，输出一个目录：`原文.md` + `media/` + `MANIFEST.json`（每个资源一行：拿到没拿到、多少字节、拿不到的原因是 scope 还是资源权限）。**绝不静默降级** —— 少一张图就在 manifest 和文件头写清楚。
